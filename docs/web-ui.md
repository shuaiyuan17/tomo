# Local web chat

`tomo start` starts the optional web UI on **127.0.0.1:9465**. Read the private access link with `cat ~/.tomo/web-access.log`; it includes `?t=<token>`. The page removes this parameter from the address bar and uses an HttpOnly cookie thereafter. At least one existing messaging channel must still be configured.

```json
{
  "web": {
    "enabled": true,
    "port": 9465
  }
}
```

The web chat is always the owner's DM session (`dm:<owner.name>`). With no owner configured, chat stays disabled (`owner_setup_required`) until one is set and Tomo restarts. `web.ownerIdentity` is only read for older configs with several `identities`, to pick which one becomes the owner. Set `enabled` to `false` to disable the UI. Invalid web settings disable only the UI and emit a diagnostic.

## Conversations

- A message sent while Tomo is working shows at once (Queued). In the owner DM it joins the running turn when that turn is the owner's own private reply turn, like a mid-turn iMessage; otherwise it waits its turn in the session queue. Once a joining message has been handed to the model it is never retried: if the turn then fails it reads back as "outcome unknown", because it may already have run.
- Owner messages use the existing DM session, Agent queue, SDK, delivery filters, and transcript. Replies from browser input go to the browser. Messaging channels and scheduled notifications retain their normal destinations.
- Groups are read-only: select a group to inspect its history and recorded context use. Browser group writes are refused by both the HTTP service and daemon.
- **Stop** takes the Send button's place while a turn runs and the composer is empty (type something and Send is back: a message sent mid-turn still joins or queues). It calls the SDK's `interrupt()` on the owner conversation's live session (`POST /api/v1/stop`: CSRF, epoch, owner): the turn ends at the SDK's next checkpoint and settles normally with whatever it had already said, the session and its background tasks stay (the owner session declares the SDK's `perTaskStopAffordance`, without which an interrupt would also kill background agents; one task is stopped from its own view, below), and nothing is reported as an error. It stops whichever turn is running in the owner conversation, including one started from a messaging channel. Text already delivered is not recalled. If that turn is a scheduled job's run, the run is recorded as interrupted, never as finished: a one-shot is parked (kept, disabled) and Tomo asks at once whether to run it again; a recurring job waits for its next normal slot. It is never re-run on its own.
- The status line above the composer says what the SDK reports about the running turn: `Retrying 2/10 · claude is overloaded` (`api_retry`), `Bash · 42s` for a tool call running longer than ten seconds (`tool_progress`; the daemon forwards a report at most every ten seconds per call and the page counts in between), and a refusal that continued on a fallback model. When the turn is over it says how it went where the SDK said more than done/failed: `Stopped`, the typed API error (`Claude login expired. Send /login to sign in again — not answered`, usage limit, billing, overloaded, …) or which model declined. These are of the moment: a new turn clears them and a reload starts without them. Superseded text from a refused attempt is not retracted (blocks are delivered and recorded one by one as they complete). The line is shown in the destructive (error) colour while it reports a failure (not sent, delivery failed, outcome unknown, interrupted, a typed API error, a refusal nobody answered), never for progress, `Stopped`, `Completed` or the explanation that a group is read-only.
- After a turn the SDK may predict the owner's next message (`promptSuggestions`, on only for the owner's DM session while the web UI is enabled). It shows as one quiet chip above an empty, idle composer; clicking it fills the composer and sends nothing. The next turn withdraws it. A leading harness stamp is stripped from it.
- A folded run of tool calls is summarised by what the calls did, in order of first use ("Read 3 files, ran 2 commands, edited a file"); while one is running the line ends with that call's title. A Bash call is titled by the short description the model wrote with it ("Run the test suite") when there is one, with the command itself inside the row; other calls keep their summary (`Read src/web/http.ts`).
- What the agent does in a turn shows as **Trace** lines (shadcn's Trace, `web/src/components/ui/trace.tsx`), the same in the chat and the task view: an icon, a title, an optional description (a duration such as `4s`, a count), and a state — a running line shimmers, a failed one is in the error colour and says so to a screen reader. Each opens in place to its detail. A folded run of tool calls is summarised by what the calls did, in order of first use ("Read 3 files, ran 2 commands, edited a file"); while one is running the line ends with that call's title. A Bash call is titled by the short description the model wrote with it ("Run the test suite") when there is one, with the command itself inside the row; other calls keep their summary (`Read src/web/http.ts`).
- **To-dos.** The agent's todo list (the SDK's `TodoWrite` tool) is one line per turn, "To-dos · 3 of 7 done", however many times the turn rewrote it: it shows the turn's latest list (a call that failed did not change it) where the first one was written. It opens to what is in progress (by its present-tense `activeForm`, shimmering while the turn runs), what is left and what is done. It is open while its turn runs and folds once the turn is over, unless you opened or closed it. The list is parsed on the server (`todoList` in `src/web/sdk-transcript.ts`): at most 50 entries ("+N more"), 400 characters each, scrubbed and, in the chat, redacted like tool output. A `TodoWrite` whose input is not that shape stays an ordinary tool row.
- **Sources.** Under a turn's tool lines, one folded "Sources" line lists the pages the turn used: each `WebFetch` URL and each link its `WebSearch` results named (the `Links:` lines Claude Code writes, or `search_result` blocks), once the call finished without an error, deduplicated by URL, with the page's title when known and its host. Links follow the markdown rule exactly: http/https only, a new tab with `rel="noopener noreferrer"`, nothing fetched until clicked, no favicons. The server reads them (at most 20 links per result from its first 256 KiB, URLs to 2,048 characters, titles to 200) and leaves out any URL the UI's redaction would change, such as one with a token in its query; a withheld output's links are withheld with it. At most 50 sources per turn.
- While a turn runs, its step shows only what the agent is doing now: the latest call's title, shimmering, behind a small animated ring (Tomo's mark drawing itself; still under reduced motion) and followed by the elapsed time. The summary ("Ran 5 commands, read 3 files") replaces it when the turn is over.
- A background task reporting back into the conversation (the SDK's task notification) is a step of its own: "Message from subagent · <description>" opening to the report it handed back, or "Background task · …" for a shell. A subagent's own call is titled "Subagent · <what it was sent to do>" and its result is labelled Report. Both are bounded and secret-scrubbed like tool output. In the main chat a report that names `memory/private` is withheld whole, like the output of a call that reached it; this is best effort (a report can quote private content without naming where it came from).
- A turn that ended without a reply (silent by choice, or stopped before it said anything) shows as "No reply" rather than the literal `NO_REPLY`.
- Replies appear one completed content block at a time. Tool activity shows names and status from attributed watch events; tool arguments and results are omitted.
- With `showThinking` on, a thinking block (text the daemon marks with `💭 `) shows as a folded, muted "Thinking" row in the sans, never as the reply; it opens in place. A live block is thinking as a whole. A recorded turn stores its blocks joined by single line breaks, so there the row takes the marked line and the paragraphs that follow it after blank lines, and ends at the first single line break (where the next block was joined on). Thinking that itself contains a single line break (a list) therefore ends early and its remainder shows as text: the reply is never folded away. Inline tool calls never include thinking.
- History is the canonical transcript, including recorded replies that may have been silent or failed delivery. It is not a read receipt. Existing transcript policies are preserved. The current request status separately reports web delivery failure.
- **Scrolling** never moves you against your intent. Opening or reloading a conversation lands on its last question, with its answer below it (or at the end, when that last exchange fits on screen). A message you send moves near the top of the view, under a slice of the previous message, and the reply grows into the room below it; once the reply fills the screen the view follows its end. The view follows new content only while you are at the end: scrolling up (wheel, touch, keys or the scrollbar) or jumping to a quoted message lets go, and a message arriving meanwhile, even a new question from a messaging channel, does not pull you to it. "Load earlier messages" keeps your place, and pictures loading or tool groups opening do not move what you are reading. While there is conversation below you and either something new arrived or the end is out of view, a pill above the composer says how many messages are new ("2 new messages") and jumps to the end, where the view follows again; focus stays in the conversation. With reduced motion, jumps are instant.
- **Tasks** (right sidebar; the topbar checklist button pins it open or collapses it, badges the running count, and is remembered per browser; at 1024 px wide or less it slides over the conversation instead of narrowing it) lists running subagents and background tasks for the owner's DM and each group: description, elapsed time, and `Working · <latest step>` when the SDK reports progress (the task type is in the tooltip). A task that keeps running after Tomo has replied (one in the SDK's background set) carries a quiet `background` tag before its elapsed time; a task the turn is waiting on has none. The list itself offers no actions. Nested tasks are indented under their parent. Watchers and other ambient tasks are hidden unless **Show watchers** is ticked. A finished task stays for about a minute, marked Done/Failed/Stopped/Ended. The [`/tasks` chat command](commands.md#tasks) reads this same board for one chat's session, plus finished tasks kept for the rest of the day (never sent to the browser). Source: the SDK's `background_tasks_changed` (REPLACE) set plus `task_started`/`task_progress`/`task_updated`/`task_notification`; prompts are never carried. Only sessions the browser can already read appear: groups, and the one DM key the session catalog shows as the owner conversation. The reconnect snapshot is complete, with shortened descriptions and summaries. The panel shows at most 128 tasks: running tasks first (watchers last), shared fairly across conversations; a task that does not fit appears as soon as there is room. On narrow screens the overlay takes focus, keeps it until closed, and closes with Escape.
- **Scheduled**, under the task list, shows the next five enabled cron jobs (soonest first; the same jobs, groups included, as the Study's Cron tab): name, when it runs next ("in 12 min", "Tomorrow 8:00 AM") and whether it repeats or runs once. Click a job to open it, scrolled to and highlighted, in the Study's Cron tab (`#study/cron/<jobId>`); **View all** opens the tab. Times refresh every minute; the list re-reads when a job fires or finishes, on reconnect, and at least every minute. Hidden when nothing is scheduled.
- Subagent cards show a model-written one-line progress summary about every 30 seconds (`agentProgressSummaries`, forked off the subagent's own prompt cache), instead of only the name of its last tool.
- A subagent's card and view show its model as a small badge (e.g. "Opus 5.5"), read from the first assistant entry of its transcript once it exists (the SDK's task events carry no model). Shell and other tasks have none.
- Click a task to read it. A running task of the owner conversation has two controls under its title: **Stop task** (the SDK's `stopTask`; the turn and the session carry on and the task ends as Stopped) and, for a task the turn is waiting on, **Move to background** (the SDK's `backgroundTasks` for the tool call that started it, the terminal's Ctrl+B: the blocking call returns at once, Tomo's turn continues, and the task reports back when it is done). Both go through `POST /api/v1/sessions/<id>/tasks/<taskId>/stop|background` with the same gate as a message (CSRF, epoch, owner) and act only on a task the panel currently shows as running; the answer is `{done}`, false when the SDK did not take it (the task had just ended), which the view says in one quiet line. The row changes when the daemon reports the new state. A group's tasks stay read-only (`403 owner_dm_only`). Everything else in the view is read-only. A subagent shows its transcript in order: assistant text, then each tool call folded to one line (`Read src/web/http.ts`, `Bash: npm test`) that expands to its input and output (capped server-side at 4,000 characters each; "Show more" expands within that cap). Its thinking is a folded, muted "Thinking" row that opens to the text (clipped at 8,000 characters like other text); thinking between tool calls folds into their group. Empty or redacted thinking shows nothing. An image in a tool's output is a small "Image output, not shown" chip: its bytes are never served. The subagent's own prompt is not shown. Long transcripts load the newest page first; "Load earlier" pages back. While the task runs, the view polls every 2 s for the lines appended since the last read, and reads once more after it ends. Shell and Monitor tasks show the end of their output (the SDK's `get_task_output`, at most the last 8 KiB, escape sequences stripped). Only a task the panel currently shows can be opened (the exact set the panel's send gate last published, after expiry, the owner rule and the capacity share), and tool input/output is secret-scrubbed like the logs. Pages never split a transcript entry; an entry with more than 400 blocks shows the first 400 and says how many it left out. At most 2,000 items stay in memory; whatever is dropped can be loaded again ("Load earlier" / "Load newer"). Both this view and the inline tool calls read the SDK's on-disk transcripts with Tomo's own bounded reader, not the SDK's `getSubagentMessages` / `getSessionMessages` (which read and parse the whole file on every call and page only by slicing the result, so a 2-second tail would re-read the file each time). Everything the reader knows about that format is in `src/web/sdk-transcript.ts`, and a test runs the SDK's readers and Tomo's over the same transcript files and requires them to agree on tool calls, results, text and thinking, and on the parsed todo lists and web pages, so an SDK upgrade that changes the format fails a test rather than emptying the view. A line the reader does not recognise (not JSON, no record type, a message without content, an unknown or malformed content block) is never dropped silently: the view says "Some entries could not be read." (the chat: "Some tool calls could not be read"), and the daemon log gets one warning per transcript file, naming only the view, the count and enumerated reasons. The main chat's scan parses only lines that can hold a tool call or result. The tool input/output section and the Terminal view are adapted from AI Elements (Apache-2.0); the license ships as `dist/web-assets/THIRD_PARTY_LICENSES.txt`.
- **Sub-sessions** (your long tasks on `task:<id>` keys) are listed first in the rail, in their own group: id, title, state (Working, Waiting for you, Needs you, Queued, Done, …) and, while it is open, the plan step it is on. **Needs you** is a finished task whose report asks you to do something (review and merge a PR, make a choice), shown with what it asks; it is listed with the open tasks, however long ago it finished, until you say it is done: tell Tomo, or send `/s <id> done` in your Telegram or iMessage DM. Only tasks your own conversation owns are listed (`GET /api/v1/subsessions`, read by the daemon from the task table); an ended one stays 72 hours, archived ones never show. Click one to open it as a chat inside the rail, beside the conversation. Under its header, **What it's doing** is a checklist the task keeps with `task_plan`: the steps it finished, each with a one-line result (the newest three, the rest behind **Show earlier**), then the one it is on and those still ahead (an open task only). **Decisions and updates** lists, newest first, what it recorded with `task_update` (a scope change, an approach chosen, blocked or unblocked) and its milestones (started, waiting for you, finished, reopened, cancelled, failed), three before **Show all**. There is no separate progress line the task writes: the step in progress is what it is doing now, and the state line (Working, with the shimmer) is the harness's own sign that a turn is running. Below that: its brief (and your words it was started from), what you and the task said to each other (your messages, its `task_reply` / `task_notify` / `task_ask`), and its report once it finishes. The box under it writes to the task exactly as `/s <id> <text>` in your DM does (`POST /api/v1/subsessions/<id>/messages`, body `{requestId, text}`, same gate as a message: CSRF, epoch, owner); the daemon accepts it only for a task your DM owns that has not been cancelled or failed, and a retry with the same `requestId` is not delivered twice. This is the only write the browser has outside your DM: groups stay read-only. The rail and an open chat follow the task live (a `subsessions` event, coalesced to at most one per 250 ms, whenever the task table changes or one of its turns starts or ends). Back to the list with **Tasks**.
- Each message shows its time ("6:32 AM"; the full date in its tooltip) and its channel as the product spells it (Web, Telegram, iMessage). A divider names the day ("Today", "Yesterday", a weekday within the week, otherwise the date) above the first row shown (outside the rows, so "Load earlier" only changes its text) and wherever the day changes, drawn at the end of the earlier row, so no row ever changes at its top and a prepended page never moves what you are reading. A message still waiting after the history (an interrupted one kept until resent or dismissed) never announces a day earlier than the message above it. Tables scroll sideways rather than break a word.
- Messages keep single line breaks (as typed in iMessage); code blocks and markdown lists are unaffected. A fenced code block in rendered markdown has a copy button (top right, on hover or focus; always shown on touch screens) that copies the code exactly, and a quiet label when the fence names a language. There is no syntax highlighting: the highlighters available colour tokens with inline `style` attributes or an injected `<style>`, which the CSP refuses. Tool input/output panes are plain text and have no copy button. Images and stickers sent from a messaging channel show as thumbnails (click for full size), documents and files as a named chip — never the stored path. Images are served by `/api/v1/sessions/:id/media` (cookie-authenticated, same-origin image fetches only, `no-store`). Transcripts keep no structured attachment record, so a file is served only if a history page this process served for that visible session named it in the leading marker of an inbound user message from Telegram or iMessage, its name carries that session's own channel-chat prefix, its real path is under `memory/incoming-images` (not `memory/private`), it has a single link, its bytes are a PNG/JPEG/GIF/WebP/HEIC signature matching its extension, and it is at most 15 MB. At most 20 thumbnails show per message ("+N more"). iMessage replies show the quoted message as a small card; when the original is in the conversation, clicking the card scrolls to it and highlights it.
- **Reply and react** (owner conversation). Hovering a message (on touch screens, always) shows its actions, adapted from AI Elements' `MessageActions` (`web/src/components/ai/message-actions.tsx`): **Reply**, **React** and **Copy** (copies the text without tomo's markers or thinking). A group shows Copy only. Both reach the agent exactly as the same gesture on iMessage does (`src/channels/text-utils.ts`), so the agent needs no web-specific handling. **Reply** puts a "Replying to …" chip above the composer (Esc or × cancels). The next message carries `reply: {text}` and is handed over as `[replying to: "<first 60 code points>"] <text>`. **React** opens the six iMessage tapbacks. A reaction is a message of its own (`reply: {text, reaction}`, no text or attachments), handed over as `[reacting to: "…"] [tapback: love]` like an inbound iMessage tapback. It never touches the draft or moves the view. The quote is the message's text without markers, at most 2,000 characters. The request keeps 200 code points of it for its pending bubble, and the journal keeps that copy with the text until the request settles, so an interrupted reply or reaction can be resent as it was. A tapback record (from the web, an iMessage tapback or a Telegram reaction) shows as one quiet line ("👍 You liked “…”"), not a bubble, plus a pill on the message it reacted to (found like a reply quote). Tomo's silent `NO_REPLY` to a tapback is not shown. One reaction per sender per message, the latest winning. Taking a reaction back is not offered: the transcript is append-only, and iMessage does not report removals to the agent either.
- **Tomo's reactions on web messages.** `react_to_message` now works on the web channel: `WebChannel.reactToMessage` takes the request id the message was received under (what the agent records as the latest inbound message), publishes a `reaction` event and keeps the last 256 in `data/web/reactions.json`. The bootstrap carries them as `reactions`. They show as a pill tagged with the agent's name. An unreadable file is left alone, and reactions are then kept in memory only. Substring targeting (`match`) is not supported on the web, which keeps no recent-message ring.
- The Plan usage card also shows the SDK's live rate-limit state (`rate_limit_event`) the moment it changes: "5-hour limit almost reached · 91% · resets in 2h 00m" or "… reached", and re-reads its bars then. Nothing is shown while usage is allowed.
- **Plan usage** (sidebar, under the context window) shows the Claude subscription windows that `/usage` prints: 5-hour and 7-day with a bar, percentage and time to reset, and per-model windows folded under "By model". It is read with the same reader (Claude Code's OAuth login), cached in the daemon for 30 minutes; the refresh button forces a read at most every 30 seconds. The card refreshes itself every 30 minutes while the tab is visible. 80% or more is shown in a warning colour. Failures are named (no login, expired login, network, timeout, endpoint error, unreadable response); a failed read keeps showing the last good numbers.
- **Compact context** (the fold icon by the context window, owner conversation only) asks Tomo to compact: after a confirm, `POST /api/v1/compact-request` (CSRF, epoch, owner) queues the same housekeeping event as the automatic compact nudge (`context-nudge`, name `compact`, delivery suppressed) noting that the owner asked from the web; Tomo runs the lcm compact skill itself. It is refused (409 `tasks_running`) while the owner's session has running non-ambient tasks, and the button is greyed then; a second request while one is outstanding answers `already_requested`. The button shows "Requested…" until context clearly drops or ten minutes pass.
- Context uses the same persisted `contextUsed` / `contextMax` values as the CLI. Estimated values are labeled. A missing window is unavailable.

## The Study

**The Study** (left sidebar, or `#study/<page>`) is a view of the workspace; apart from the cron actions and the model switch below it is read-only. Every read uses the same authentication as chat and runs in the web process, never on the daemon thread.

- **Todos:** the open items of the [todo store](todos.md) (`GET /api/v1/todos`), grouped by who moves next: waiting on you, on the agent, on someone else. Items past their review date are marked due and listed first; each shows its next step, its `ref` (a link when it is a URL or `owner/repo#123`), and how many of its snoozes are used. The summary shows the open count against `todos.maxOpen`, and **Recently closed** unfolds the last 20 entries of the done log. The page shows what `/todo all` shows in your own conversation (your items and every group's) and is read-only: todos are added and resolved through the agent's todo tools and `/todo`, and the web process never takes the store's lock or writes its files. A store that cannot be read is reported as unavailable, never as an empty list.
- **Memory:** browse `MEMORY.md`, topic files and subdirectories; search literal text and open results.
- **Context:** for the conversation selected in the sidebar (owner DM or a group): persisted window usage and breakdown, the same estimated sections as `tomo lcm stats`, retained rollup blocks as in `tomo lcm blocks`, and compactions seen since the daemon started (not a complete audit log). A missing window is unavailable, not zero. The window is one meter: the percentage used with its state in words ("Room to spare", "Filling up" from 80%, "Nearly full" from 95%; the meter's colour follows the state), split into the conversation (`Messages`) and what is loaded on every turn (system prompt, tools, skills, memory), then the compact buffer and the free rest. The breakdown lists only what occupies the window, largest first; tool definitions the SDK reports as `(deferred)` are listed apart as not loaded. When the breakdown does not measure the current reading (the reading is an estimate, or the rows do not add up to it because they are kept from the last full reading), the meter is one undivided piece and the rows are labelled as that earlier reading, with shares of its own total. Rollup blocks are a timeline, newest first, titled by the period they cover with the number of events each summarises.
- **Model** (`#study/model`): the model the conversation selected in the sidebar runs on (its `sessionModelOverrides` entry, else `config.model`), its reasoning effort and where it comes from (the session's `sessionEffortOverrides` entry, `config.effort`, unset so the SDK default applies, or not sent because the model is a LiteLLM `provider/model`; the same rule `sdkOptions` sends), then the models `/model` offers by alias (`GET /api/v1/models?session=<id>`). The owner's own conversation can be switched: pick a row, or type any other id `/model` would accept (a direct model id, or a LiteLLM `provider/model` when a gateway is configured), and confirm; the conversation continues on the new model from the next message, with its history and SDK session kept. The switch (`POST /api/v1/models`, body `{sessionId, model, from, confirm: true}`) runs the same shared function as `/model` in the daemon: the same name resolution and gateway checks, the same locked write of `sessionModelOverrides` to `config.json`, and the same live-session restart. Unlike `/model` it is refused while a turn is in flight on that conversation (`409 turn_in_flight`) instead of cutting the turn off, and when the model is no longer the one the page showed (`from`; `409 model_changed`). An unknown name is `422 unknown_model`; a gateway model without a gateway, or one the ChatGPT-subscription gateway does not route, is `422 gateway_required` / `422 gateway_unroutable`; a failed write is `503 persist_failed`. Nothing is saved on any refusal, and choosing the model already in use changes nothing. Groups show their model but are read-only here (`403 owner_dm_only`); use `/model` in the group. Open pages re-read after a switch.
- **Cost** (`#study/cost[/<YYYY-MM-DD>]`): what Tomo's work would cost at API list prices, from the usage ledger through `GET /api/v1/cost` only (every dollar figure is marked EST.; it is the SDK's estimate, never a bill). Left: a ten-week calendar heatmap (days before the ledger started are blank and cannot be picked; days before the #389 fix are dashed boxes, flagged over-counted and never compared), At a glance (this week vs the week before, 30 days, the median and busiest fair day), and Who started it / Scheduled jobs over 7 or 30 days. Right: the picked day (default today; the date goes in the hash with `replaceState`, so a reload keeps it and Back leaves the Study): its cost against a typical day, turns, cost by hour split You / Background / Scheduled, and its six costliest turns with their trigger (group messages included), conversation, duration and tool calls. A plan usage bar at the top shows the newest 5-hour and 7-day sample from `limits.ndjson`, and is hidden without one. An empty ledger says nothing is recorded yet.
- **Cron:** names, schedules, target sessions, messages, next/last runs and status, read fresh from the scheduler's store file. The daemon hands the web process that path; the web process reads it asynchronously (at most 4 MiB, `413 cron_store_too_large` beyond), refuses symlinks, FIFOs and other non-regular files, and parses it with the store's own side-effect-free parser. Each job can be paused, resumed or deleted after a confirmation that names it. The change passes the same bounded read, then goes through the store's own guarded, locked load-modify-save (as `tomo cron` does) and only if the job still has the intent you reviewed (name, schedule, message, session, enabled, one-shot); a run starting or finishing meanwhile does not invalidate it, an edit does (`409 cron_changed`). A run already in progress is not stopped. Resuming a one-shot whose time has passed runs it at the scheduler's next check; a recurring schedule with no future run is refused (`422 unschedulable`).
- **MCP servers:** saved definitions, including disabled ones, with the state live SDK sessions report (connected, failed, needs sign-in…). Health is never probed and no connection or OAuth flow is started; no report means unknown.
- **Config:** the saved `config.json`. Values the daemon is running with may differ until it restarts.

The Study's only writes are the cron actions and the model switch. Like a message, each needs the exact Origin, the session cookie, the CSRF header, a JSON body with `confirm: true`, and the daemon epoch the page loaded under (`409 epoch_changed` after a restart). A definite CSRF rejection is retried once with a refreshed token; nothing else is retried.

`memory/private/` is never listed, read or searched by the Study, not even for the owner. It uses the agent's own private-memory fence (`landsInPrivate`: lexical, real-path and case-folded), a private path reads as not found, and `MEMORY.md` lines that link into `private/` are withheld, as in group prompts. Config strings are shown only on an allowlist of known non-sensitive paths (`SHOWN_STRING_PATHS` in `src/web/config-view.ts`: models, modes, channel / chat / session identifiers, time zone, paths, tool names, MCP `type`), and even then not if the value looks like a credential. A path with a wildcard (`sessionModelOverrides.*`, `identities.*.channels.*`, `plugins.*`, …) shows its keys, but a value only when it passes that path's check (a model id of at most 64 characters, a chat id, a lowercase channel name, a file path, …); a wildcard path without a check never shows a value, and a key that looks like a credential is shown as `•••`. Every other string, including any field added later, shows as `•••` with its length. Numbers and booleans are shown unless a path segment names a credential or they are an opaque MCP value (anything but `type`, `enabled`, `disabled`, `timeout`, `alwaysLoad`).

Study reads are bounded: Markdown files to 256 KiB; the tree to 1,000 entries, eight levels and a time budget; search to 100 hits, 4 MiB and a time budget. Symlinks, hard links and special files are rejected. Context analysis reads at most 16 MiB of SDK transcript one JSON line at a time (256 KiB per line, 20,000 lines) and returns at most 100 sections and 100 rollups (8,000-character previews); a larger transcript keeps its persisted window reading. One workspace/context inspection runs at a time across browser clients (`429 inspection_busy`, retried by the page); chat stays available. MCP status covers at most 32 live sessions and times out after one second.

## Home

**Home** (left sidebar, or `#home`) shows Tomo's home: a small low-poly 3D room that Tomo designs as data (`src/home/scene.ts`) and that shows what Tomo is doing. It takes the whole main area; at phone width the room fills the width and the height between the header and the caption, and the camera looks down more steeply on a tall view so the room fills it. Drag (or swipe sideways, or use the arrow keys while it has focus) to turn it within limits; double-click or Home puts it back at its default angle. Vertical swipes still scroll the page (`touch-action: pan-y`).

Under the room one quiet line says in words what is happening, from `HomeStatus` alone ("Working on your message · 2 subagents", "Running a scheduled job", "Idle for 20 min", "… · retrying", "Compacting context"), with the weather last when the daemon reports it ("12°C, raining"). A note says so when the starter room is showing, and when Tomo's latest scene has a problem (the room is then the last good one; the problems are listed under the note).

Data flow: the page reads `GET /api/v1/home` (`WebHome`) when it opens, again on a `home` event and after every reconnect, and at least once a minute while it shows in a visible tab (the daemon takes a recent read as "someone is looking"; reads made for the other reasons count), and applies `home-status` events live (the newer by the daemon's `status.at` wins, so a GET and an event that cross never go backwards). Times in the status are moved onto the browser's clock with `status.at`, as the Plan usage card does. Without `status.sky`, `day` / `night` and the window's sky come from the viewer's own clock (dawn 6–7, day 7–18, dusk 18–19), clear.

When Tomo asks to look (`home-look`) **while the Home page is showing**, the page renders one frame, scales it down until the PNG fits `HOME_SNAPSHOT_MAX_BYTES`, and posts it to `POST /api/v1/home/snapshot` (`homeSnapshotSchema`; CSRF and epoch like every mutation). Nothing is ever uploaded unasked, and a look while another page shows is not answered.

The drawing:

- three.js is in its own chunk (`web/src/home/room-view.tsx` and `web/src/home/three/`), loaded only when the Home page opens; the chat bundle only gains the page shell and the caption. Without WebGL, or if that chunk fails to load, the room area says so and the caption still works.
- What holds (conditions), what each part's reactions come to, sign text, who sits where and the sky are pure functions (`web/src/home/evaluate.ts`, `layout.ts`, `caption.ts`, `sky.ts`) with unit tests; three.js only draws their results.
- Shapes share one unit geometry each and one material per colour; parts that glow or change colour get their own. Placement follows the format's PLACEMENT rules (`src/home/scene.ts`), as the checker and Tomo's floor plan do: `at` is the base centre, `turn` goes around x, then y, then z; `size` sizes only a shape, picture, sign or window; `scale` multiplies a part and everything in it uniformly (not what rests on it). Kinds are expanded into instances. `on` places an object in the other's turned frame at its top centre (a shape's own height; for a group or kind instance the centre of the top of its bounding box), so it moves and turns with it; an `on` that is missing or loops leaves the object standing in the room. Signs are canvas textures redrawn only when their text changes; a sign whose text comes out empty is not drawn. Pictures are loaded as images only (an SVG too), drawn at most 1024 px. A window's sky is a canvas the page draws (phase gradient, sun or moon by `progress`, stars, clouds, rain, snow, fog, the odd lightning flash); the sky outside also dims and cools the scene's light a little at night and under heavy weather.
- Reaction defaults (`REACTION_DEFAULTS` in scene.ts, mirrored in `web/src/home/contract.ts` and pinned by a test): `bob` 0.06 m at 1.2/s (at most 1 m), `spin` 0.25 turns/s, `swing` 12° at 1/s, `pulse` 8% at 1/s (at most 50%); `speed` is cycles per second. With several reactions of one kind holding, the first wins; any `show` makes a part visible only while one holds, and a holding `hide` wins.
- Visitors keep their seat for the life of their subagent; newcomers, and those waiting, take the lowest free seat. Up to eight wait in a row at `overflow`. The pet is drawn when the scene has one and the status reports a mood.
- Characters walk between spots, reactions fade and ease. With `prefers-reduced-motion` nothing moves: states (glow, show / hide, where everyone is, the sky) are applied at once.
- It renders only while something changes or moves (ambient motion at 30 fps), never while the tab is hidden or another page is showing, caps the pixel ratio at 2, uses a fixed pool of two glow lights (so no shader recompiles), caps the nodes it builds and the sign pixels it allocates, and disposes everything, its WebGL context included, when the page closes.

## Screen

**Screen** (the monitor button next to Tasks in the top bar; shown only with the owner conversation selected, on macOS) opens a read-only live view of the Mac's main display in a floating, non-modal window. It opens bottom right, about 480 px wide and 16:10, clear of the composer. Drag its title bar to move it and its corner to resize it; position and size are remembered per browser and pulled back inside the window on restore. Double-click the picture (or the full-screen button) for full screen. Esc closes it while it has focus; the top-bar button or × closes it too, and closing stops the stream. On phone widths it is a bottom sheet. Nothing in it sends input to the Mac.

The colour theme (system / light / dark) sits at the bottom of the left sidebar; at phone width the sidebar is a drawer (see Phones) and the switch is at its end. The browser's own colour (`theme-color`: the tab strip, a phone's status bar) follows the chosen theme, and the tab title names Home, the Study page or the group being read.

- The web process runs a small JXA helper (`osascript -l JavaScript`, part of macOS: no compiler or Xcode needed) once per frame. It reads this process's own login session (`CGSessionCopyCurrentDictionary`) and only if that session is on the console, logged in and unlocked does it capture the main display (`CGDisplayCreateImage`), scale it to a longest edge of 1600 px and encode JPEG at quality 0.6, all in memory, printing the result to its stdout. No frame is ever written to a file, and frames never cross the daemon IPC. The helper is killed after 5 seconds.
- Frames reach the browser as an SSE stream read with `fetch` (`GET /api/v1/screen?fps=…&epoch=…`), as base64 JPEG shown through a `data:` URL that the existing CSP already allows. The stream carries the same cookie, custom header and same-origin checks as every other API; it needs the current daemon epoch and is sent `no-store`.
- One capture loop serves every viewer, at the fastest rate any of them asked for (0.5, 1 or 2 fps), with one capture in flight at most. It runs only while a stream is open. The page closes its stream when the view is left, paused, or the tab is hidden, so with no viewer the Mac is not captured at all. A frame is skipped for a browser that has not drained the previous one. At most 4 streams.
- Fail closed: a locked screen, a session not on the console, or a lock state that cannot be established (helper failure, timeout, missing fields) is reported instead of captured ("Can't confirm the screen is unlocked"); a failed capture is reported as unavailable. The last picture then stays greyed out and labelled with its age, never shown as live. A capture that returns after the last viewer left is discarded. Without the Screen Recording permission macOS still returns a picture with only the desktop wallpaper; that cannot be detected cheaply, so the page says how to recognise it.

## Home

**Home** is Tomo's home: a low-poly 3D room Tomo designs as data and the page draws, to show what Tomo is doing. This section is the server side; the page and renderer are described with the browser code.

- **The scene is data.** Tomo writes `<workspace>/home/scene.json` with its ordinary file tools, and pictures into `<workspace>/home/assets/`. The format is `src/home/scene.ts` (zod schema, closed CONDITIONS / REACTIONS lists, limits); nothing in it runs. The daemon checks it whole (`src/home/check.ts`: references, kind cycles, duplicate ids, exactly one of shape/kind/picture/sign/window, expanded part count and depth, parts far outside the room, characters' kinds and spots, pictures present in `assets/`), keeps the **last good** scene (persisted to `~/.tomo/data/home/last-good.json`, so a restart with a broken file still shows a room) and falls back to the starter (`src/home/starter.ts`) when there has never been a good one. A broken write never takes the room down: the page gets the last good scene plus `problems`. The starter is written to `home/scene.json` on first start (never over an existing file). Changes are noticed by `fs.watch` on the workspace, `home/` and `home/assets/` (200 ms debounce) with a 5 s stat poll as fallback; a missing, deleted or replaced folder is handled.
- **Files are confined.** `home` and `home/assets` must be real directories exactly there (by real path; a symlinked folder reads as missing), every file an ordinary single-link file opened with `O_NOFOLLOW` and re-checked after opening, the scene at most 256 KiB (`MAX_SCENE_BYTES`). A JSON syntax error is reported by line and column only, never quoting the file.
- `GET /api/v1/home` → `WebHome` `{ scene, revision, starter, problems?, status }` (RPC `home`; the web process re-validates the scene before serving it). `revision` covers the served scene, its problems and every asset file (name, size, mtime, inode). `starter` is true while the served scene is the starter (the fallback, or a file still identical to it).
- `GET /api/v1/home/assets/<name>` → the picture, cookie-authenticated and, like the media route, only as a same-origin image fetch (`Sec-Fetch-Dest: image` or `empty`). The name must match `ASSET_NAME`; the file must be an ordinary single-link file of at most 512 KiB in the real `home/assets`, its bytes the type its extension says (PNG, JPEG, WebP by signature; SVG by its first element). Served `no-store`, `nosniff`, with its content type; an SVG also with `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`. Every refusal (traversal, symlink, hard link, wrong type, too large, missing) is the same 404; nothing under `memory/private` can be reached.
- `POST /api/v1/home/snapshot` (`homeSnapshotSchema`: `{ requestId?, revision, png }`): exact Origin, cookie, CSRF, the current daemon epoch (`409 epoch_changed`). This route alone may send more than `MAX_BODY_BYTES` (up to the schema's base64 bound plus 1 KiB; beyond, `413`). The PNG signature, IHDR and size (at most `HOME_SNAPSHOT_MAX_BYTES`, sides at most 8192) are checked in the web process and again in the daemon (RPC `home-snapshot`), which keeps the latest picture in memory and hands it to the `home_check` call whose `requestId` it carries.
- Events: `home { revision }` when the revision changes; `home-status { status }` when the status record changes (at most 4 a second, the last change always delivered; a sky's progress moves in hundredths); `home-look { requestId }` when Tomo asks to see the room.
- **Status** (`HomeStatus`, `src/home/status-reducer.ts`) is derived from the watch bus: turns (the owner's wins for `by`), the kind of tool in use, subagents and background tasks (ambient excluded), cron, compaction (the SDK's own, or Tomo running `tomo lcm compact`), trouble (retry, rate limit, API error, each with its own end), `idleSince`, the next enabled job, the pet's mood, and `sky`. A subagent's `task` text is filled in only for sessions the Tasks panel would show (any group; the DM the catalog shows as the owner conversation).
- **Sky.** With `city` configured, the window's weather comes from `https://wttr.in/<city>?format=j1` (only the city is sent, as for the heartbeat): one request at a time, 5 s timeout, 512 KiB cap, cached 30 minutes (a failure 5), and only while someone is looking (a page read `/home` or `home_check` looked within two hours). Day, dawn, dusk and night are computed from the area's latitude and longitude (NOAA solar position; twilight between −6° and +6°), not from the answer's local-time strings, so no time zone is assumed. No city or no usable answer: no `sky`, and the page shows a clear sky by the viewer's clock.
- **Tomo's tool** `home_check` (tomo-internal MCP, the owner's DM session only, refused while a summoned group steers the turn) checks the live scene or a draft `.json` directly in `home/`, returns problems, warnings and a text floor plan (`src/home/floor-plan.ts`), and for the live scene asks an open Home page for a picture (`home-look`), waiting up to 6 s. A page showing the home re-reads `GET /api/v1/home` at least every 60 s, so the daemon counts a read in the last 90 s as "a browser has the home open": with none (or no web UI) `home_check` answers at once that there is no picture, sending no `home-look`; with one, it asks and waits. A page that does not answer in time also reads as no picture.
- **Group turns cannot change the home.** On a group (or summoned) turn the file tools may read `home/` but not write it, and the sandboxed shell is denied writes under it (see CLAUDE.md, "Tomo's home").

## Credential card

With `credentialBroker.enabled`, a `request_credential` made on a turn that came in on the web UI is asked here, not in a chat (`src/credentials/`; iMessage and Telegram turns are asked in that private chat). The server side copies the Home snapshot route's pattern:

- **Event** `credential-request { request: { id, name, purpose, expiresAt } | null }`, REPLACE semantics: the request opened, or (null) it was answered, refused or expired. The bootstrap and the SSE snapshot carry the same `credentialRequest`, so the card survives a reload. Neither ever carries a value.
- **`POST /api/v1/credentials/<id>`**, body `{ value }` (1 to 8192 characters) or `{ cancel: true }` (`credentialSubmitSchema`, strict). The same gate as every write: exact Origin, cookie, CSRF, the current daemon epoch (`409 epoch_changed`), the owner (`409 owner_setup_required`). RPC `credential-submit` → `broker.fulfill(id, …)`. Answers `200 { status: "stored" | "cancelled" }`; `409 credential_unknown` (wrong id, or the request is over), `410 credential_expired`, `400 invalid_value` (the request stays open; it needs printable ASCII, 4 to 8192 characters), `400 invalid_credential` (a malformed body), `503` when the broker's state or the keychain is unavailable. Error bodies are fixed codes; nothing echoes the body.
- **Never `/messages`.** That route journals to `requests.jsonl` and draws a chat bubble; the card's route does neither, and the value never reaches a transcript, an event, a log line or a message view.
- **The page** (`web/src/credential-card.tsx`) shows the card above the composer: the name, the agent-written purpose (labelled unverified), a countdown, a `type=password` field with `autocomplete=off`, Store and Refuse. The value is read from the field (not React state), the field is cleared before the request leaves, and the card goes when the daemon withdraws the request.
- While the card is open, the owner's iMessage and Telegram messages are dropped (one may be the value) and they are told; the web chat carries on as normal.

## Permission card

A sandboxed group's `request_permission` (`src/permissions/broker.ts`) is shown above the composer, one card per group with an open request, beside the owner's DM.

- **Event** `permission-requests { requests: [{ id, code, group, path, access, reason, command?, expiresAt }] }`, REPLACE semantics (empty: none open). The bootstrap and the SSE snapshot carry the same `permissionRequests`. `path` is the harness-resolved real path; `reason` is the agent's own and labelled so; `command` is the turn's last sandboxed call, folded away by default.
- **`POST /api/v1/permissions/<id>`**, body `{ decision: "once" | "always" | "deny" }` (`permissionDecisionSchema`, strict), under the credential route's gate (Origin, cookie, CSRF, epoch, owner). RPC `permission-decide` → `broker.decide(id, …, "web")`. Answers `200 { status: "allowed_once" | "allowed_always" | "denied" }`; `409 permission_unknown`, `410 permission_closed` (answered or expired), `503 permission_config_unwritable` (Always allow could not be saved; the request stays open), `400 invalid_decision`.
- **`POST /api/v1/permissions/revoke`**, body `{ grantId }` (`G-XXXXXX`; `permissionRevokeSchema`, strict), same gate. RPC `permission-revoke` → `broker.revokeGrant(…, "web")`: removes the grant's path and record from the group's `groupSandbox` entry (config file and live policy) and logs it. `200 { status: "revoked" }`, `404 grant_unknown`, `503 permission_config_unwritable`, `400 invalid_revoke`. An Always allow answered on the card returns its `grantId`. No page uses it yet (the Permissions page is next).
- **The page** (`web/src/permission-card.tsx`): the group, Read / Write, the path, the reason, the folded trigger, a countdown, Allow once / Always allow / Deny (no second confirmation), and one line saying Allow once covers file reads and writes while shell access needs Always allow. After an Always allow, a small notice keeps the grant ID on screen (copyable) until closed.

## Reconnection and limits

An acknowledgment means the Agent accepted custody; completion is separate. A browser disconnect never cancels accepted work. The daemon retains a bounded mailbox and replay ring across web-process restarts. A replay gap reloads authoritative history. A daemon restart creates a new epoch and invalidates old mutations.

If a response is lost, use **Check message status**. The draft remains available and is never automatically resubmitted. After a daemon crash the outcome can be unknown, even when input appears in history; review the conversation before choosing to send again. Exactly-once execution across daemon crashes is not promised.

Admission limits are 16,000 UTF-16 code units (the textarea's length measure), 128 KiB JSON request bodies, 32 active requests, and 4,096 retained receipts. The byte limit accommodates non-ASCII input and JSON escaping. Oldest settled receipts are evicted at capacity; active turns, including failed deliveries that have not finished, are retained. Duplicate/conflicting IDs are detected while their receipt is retained. An evicted ID reads back as unknown; never retry an old request ID expecting indefinite deduplication. Receipts are also journaled to `~/.tomo/data/web/requests.jsonl` (append-only, `0600`, fsynced before the browser hears "accepted"), so a request ID resent after a restart is still recognised. A request the daemon accepted but never settled before it stopped or crashed is **not re-run**: it reads back as `interrupted`, its recorded bubble (if any) carries an "Interrupted" badge, and the owner's session gets one note on its next turn (the journal records the note as given only after it is written and fsynced to the pending-notes file; a failed write or a crash before that repeats the note on the next start rather than skipping it). Its full text is kept until its message is found in the transcript or the owner resends or dismisses it in the browser (on its pending bubble, or on its history bubble when the transcript has it). Every such request is always in the snapshot, outside the 128-request window. A resend dismisses the original only once the resent text (or an edit that keeps at least half of it) is accepted; clearing the composer cancels it. With 64 such requests (or half the snapshot budget) waiting, new browser messages are refused (`503 interrupted_backlog`) rather than dropping any. If the journal cannot be read, the browser takes no new messages (`503 journal_unavailable`) and the file is never rewritten. A user-directed new submission uses a new ID. Delivery uses a 2 MiB mailbox and 256 KiB maximum events. Oversized or unavailable outlets enter the existing delivery-failure path. The browser is never a prerequisite for Agent progress.

History reads are limited to 100 records per page, 1,024 files / 64 MiB scanned per request, and 2 MiB responses. Malformed cursors return 400; rotation returns 409 and the browser reloads the first page. Scan/response limits return 413; unreadable or ambiguous history remains unavailable. Pages still rescan the bounded history; use the CLI for larger archives.

## Security and operations

The web child generates a random 32-byte token in the runtime home's `web-token` file (normally `~/.tomo/web-token`), with mode `0600`. A valid existing token survives restarts/upgrades. Missing, malformed, symlinked, or incorrectly permissioned files are atomically replaced under the existing file lock; the startup log announces replacement. If the token cannot be safely persisted, the UI fails closed while messaging remains available. Usable access URLs are written to `web-access.log` under the runtime home, atomically replaced at mode `0600`. Ordinary logs redact the recognizable Web token format, including when a tool prints the token file. Keep the private access link file out of bug reports. To rotate access, stop Tomo, remove `web-token`, and restart; existing signed cookies then become invalid.

Bootstrap requires the token or an existing signed cookie. Every other API, including history and SSE, also requires authentication. Cookies are bound to the exact origin, last 30 days, and survive web/daemon restarts when the token is unchanged. HTTPS cookies are Secure. CSRF tokens expire after 12 hours; a definite `invalid_csrf` rejection refreshes bootstrap and retries once with the same request ID and daemon epoch. Network failures and epoch changes never trigger automatic resubmission.

A private token file prevents another OS account, or a sandbox/container without access to that file, from obtaining web access. It cannot stop a process already running as the owner or an environment sharing the owner's files. Exact Host/Origin checks, same-origin Fetch Metadata, a required API header, CSRF, and a restrictive CSP also protect against hostile websites. This requires a browser that sends `Sec-Fetch-Site`; older browsers without Fetch Metadata are rejected. Chromium is covered by the browser E2E suite. Assets are packaged locally; markdown cannot execute HTML/scripts or automatically fetch remote images.

HTTP, asset serving, and history reads run in a supervised process with memory, startup, IPC, and connection limits. A busy port, a crashed process, or a hung startup is retried with capped exponential backoff (up to 5 minutes) for as long as the daemon runs; the failure counter resets after 5 minutes of health. Entering backoff logs an error, and `tomo status` shows the web line (listening, or down with the next retry time and last failure). Messaging channels continue operating. No UI request can call a generic file, command, or Agent RPC.

## Private access through Tailscale Serve

Use [Tailscale Serve](https://tailscale.com/docs/reference/tailscale-cli/serve) on the same host to terminate HTTPS and forward to loopback:

```sh
tailscale serve --bg http://127.0.0.1:9465
```

Copy the exact HTTPS origin reported by Serve into `web.externalOrigin` and restart Tomo. For example, using a synthetic tailnet name:

```json
{ "web": { "externalOrigin": "https://test-node.test-tailnet.ts.net" } }
```

Use the Tailscale access link from `web-access.log` on a device in that tailnet. Preserve the original Host and Origin through the proxy. The allowlist consists of the exact local origin and this single configured HTTPS `.ts.net` origin; no wildcard, suffix-based request matching, LAN listener, or forwarded-header trust is used. Authentication remains mandatory for both origins, and cookies cannot cross between them. Tailnet access rules should also restrict who can reach the service.

**Never use Tailscale Funnel.** Funnel exposes a service to the public internet; public deployment is unsupported. Tomo does not configure Tailscale or infer whether an operator enabled Funnel. Use Serve restricted to the tailnet and check its configuration. The implementation is tested with equivalent proxy Host/Origin requests; a live tailnet smoke test remains an operator check.

All runtime paths are temporary; no real account or daemon is used. Browser screenshots are written to the ignored `test-results/` directory. CI runs lint, strict TypeScript, Vitest coverage on the existing Node matrix, and Chromium E2E on Node 24.

Loading and rendering: the chat's first paint needs the entry chunk, the React chunk (its own chunk so its hash, and the browser's cached copy, survive app releases) and one small shared chunk, all `modulepreload`ed; the Study, the screen window, the task view and the home room's three.js are lazy chunks fetched when opened (same origin, so `script-src 'self'` covers them; all CSS stays in the one stylesheet). index.html preloads the regular serif woff2. The web child serves `/assets/*` (content-hashed names) with `Cache-Control: public, max-age=31536000, immutable`; index.html, icons and the manifest stay `no-store`. JS, CSS, HTML, SVG and the manifest are compressed (brotli, else gzip, per `Accept-Encoding`) once per file version and kept in memory. Markdown uses GFM's parser only (no serializers). Re-renders are kept to what changed. The composer (`composer.tsx`) owns the draft, the attachment tray, the send state machine and the status line, so a keystroke, upload progress or the running tool's one-second clock (`StatusLine`) re-renders the composer, not the page; the rows reach it through `ComposerHandle`. Tool events are not React state: `useWeb` hands them to listeners (`onToolEvent`), and `useSessionTools` re-reads the transcript on one, changing state only when the read finds something new (`mergeTools` returns the same state otherwise), so a turn's burst of tool events does not re-render the page. Recorded messages are memoized — the markdown `Text`, `MessageBody`, the parsed send markers and reply quotes (`parseHistory`, cached per message object), and each recorded row (`RecordedMessage` in `conversation-rows.tsx`, a `memo` on props that are its own: its message, its request, its reactions, its flags, and one stable `RowActions` object). `mergeLatest` (`use-history.ts`) keeps a message object while its content is unchanged, and returns the loaded page itself when a re-read changed nothing, so a streamed block, a tool call or another request's update re-renders only the rows it touches. A new value a recorded row reads must be one of its props (derived for that row), or the row shows a stale value; never pass it a fresh object or closure per render, or every row re-renders. A lazy view whose chunk fails to load (for example a tab left open across an upgrade) shows a Reload note in its place (`ChunkBoundary`); the rest of the app stays.

`npm run build` includes browser assets in `dist/web-assets`; `npm pack` includes them in the distribution. `npm run dev` serves those built assets, so rebuild after frontend changes. The UI does not start a Vite development server in the daemon.

### UI gallery

`npm run web:gallery` builds, then screenshots every surface and state of the UI so a change can be reviewed by eye: the rich conversation (markdown, tables, code, an image, a quote), tool rows open and closed, hover and focus, the composer (focus, refused, delivery uncertain, working with a draft and an attachment), the empty chat, the phone drawer, the session menu, the Tasks rail and a subagent transcript, the scheduled list, every Study tab, the cron confirm dialog, the compact dialog, the screen window, a read-only group, Home with and without WebGL, the locked page and the disconnected state. Each is taken at desktop 1440×900, laptop 1280×720, tablet 820×1180 and phone 390×844, light and dark, at device scale 2.

It runs `tests/gallery/ui-gallery.gallery.ts` (its own `vitest.gallery.config.ts`; not part of `npm test` or `npm run test:e2e`) against the same real stack and deterministic doubles as the E2E tests. The browser clock is frozen and seeded timestamps, time zone and locale are fixed, so shots of the same code match run to run; times the server takes from its own clock (a message sent during the run) still follow real time. Shots are written as `<surface>-<state>-<viewport>-<theme>.png` to the ignored `test-results/gallery/`, with `index.html`, a contact sheet grouped by surface with light and dark side by side. A step whose control can no longer be found does not stop the run: it is listed in `failures.json` and at the top of the sheet, and the command exits non-zero. A full run takes several minutes.

```sh
npm run web:gallery                              # everything, into test-results/gallery/
npm run web:gallery -- --only study,phone-dark   # only names containing one of the substrings
npm run web:gallery -- --dir /tmp/gallery-after  # another folder (or GALLERY_DIR=...)
node scripts/ui-gallery.mjs --sheet-only         # rebuild index.html from the PNGs already there
```

`GALLERY_LOCALE=zh-CN` gives the browser another language (the UI follows it; steps that find a control by its English name then fail and are listed). `--only` keeps the folder's other shots; without it the folder is emptied first. For a before/after comparison, run it from two checkouts (for example a `git worktree` of `main` and your branch) into two folders, then open the two `index.html` files side by side:

```sh
(cd ../tomo-main && npm ci && npm run web:gallery -- --dir /tmp/gallery-before)
npm run web:gallery -- --dir /tmp/gallery-after
```
