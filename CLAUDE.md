# CLAUDE.md

## What is Tomo

Tomo is a personal AI assistant that lives in messaging apps (Telegram, iMessage). It runs as a long-running Node.js daemon on the user's machine, powered by the Claude Agent SDK. The optional local web channel shares the owner's DM session; group conversations are read-only in the browser, and the owner's own sub-sessions (`task:` keys) can be written from the Tasks rail. `tomo watch` also provides runtime observability.

Published to npm as `tomo-ai`. Installed globally via `npm install -g tomo-ai`.

Runtime data lives at `~/.tomo/` (config, sessions, cron jobs, logs, workspace, memory).

The browser frontend lives in `web/` at the repository root, uses strict React/TypeScript with Tailwind v4 and shadcn/ui components (`web/src/components/ui`, Radix primitives; the paper palette lives as shadcn tokens in `web/src/styles.css`), and builds into `dist/web-assets`. Radix overlays must stay non-modal (`modal={false}`): modal ones inject a `<style>` tag that the CSP (`style-src 'self'`) blocks. See `docs/web-ui.md` for limits and development commands. The web child never owns another Agent or writes transcripts. Owner input goes through `Agent.addChannel`; reply outlets are bound to request IDs, and web/provider turns cannot steer into each other's delivery destination. Preserve the existing persistent notification target and transcript policy.

All private web APIs, including reads and SSE, require a signed origin-bound session cookie. Bootstrap grants one only with the persistent private `web-token`; CSRF expires independently and can be renewed without logging in again. Token file I/O and locking happen in the supervised child. The HTTP listener remains loopback-only; `web.externalOrigin` permits one exact HTTPS Tailscale Serve origin, never a wildcard. Do not use Funnel or infer authentication from forwarded identity headers. Evict only settled receipts; a failed delivery can still have an active turn and must retain its outlet until settlement.

## Key Design Patterns

### Session Keys

Session keys determine conversation isolation:
- **The owner**: `dm:<owner.name lowercased>` — ONE session across Telegram, iMessage and the web UI. `owner.name` IS the session id (the same derivation the old per-identity key used), so it is never rewritten; the human-facing label is `owner.displayName`.
- **Group chats**: always `<channel>:<chatId>` — never unified (unless `/summon`ed into the owner session)
- Raw `<channel>:<chatId>` DM keys only exist as legacy history; no new one is created for anybody.

There is ONE owner (`src/owner.ts`). `config.owner` is resolved from the `owner` block or, for older files, from `identities` (read forever): one identity → it is the owner; several → `web.ownerIdentity`, else the first, with a startup warning; none → the single DM allowlist entry if exactly one exists (pre-identity installs), else no owner (every DM ignored). Other identities' sessions, transcripts and cron jobs are never touched. `replyPolicy` is ignored: replies go to the channel the owner last wrote from.

The `OwnerRouter` resolves (channel, chatId, isGroup) → sessionKey + replyTarget. At daemon start `Agent.prepareOwner()` logs owner notices, adopts a single legacy per-channel owner session if the owner key has no SDK session, and pre-creates the owner's registry entry (also done by `tomo init`). Adoption never runs once the owner key has a linked session, and `migrateSessionKey` folds a metadata-only stub under the destination key instead of creating a second active entry — so the owner session cannot fork.

**Admission fails closed** (`OwnerRouter.isAllowed`): a DM is admitted only from one of the owner's handles on that channel (DM entries in a channel allowlist are ignored — allowlists govern groups only); a group only when it is in the channel's allowlist (the group secret adds it). A channel with NO allowlist is not open. Owner-only commands go through `isOwnerSender`, which fails closed with no owner. Refused messages still return custody (`true`) so the iMessage cursor advances, and are logged once per chat per hour (`agent/blocked-inbound-log.ts`). Compare iMessage handles only through `matchesChannelBinding` / `isOwnerHandle` / `normalizeImessageHandle` — never with `===`. Agent tests run a documented admission seam (`useRealAdmission()` in `tests/helpers/agent-harness.ts`) — admission tests must opt into the real logic; `mockConfig.owner` is derived from `mockConfig.identities` through the production resolver.

**Transcript filenames** are derived from the key by `transcriptFileStem()` (`src/sessions/transcript-names.ts`, re-exported from `store.ts`) — `<stem>.jsonl` active, `_archive_<stem>_<YYYY-MM>.jsonl` rotated — and the mapping is INJECTIVE **up to case folding**, which the old `key.replace(/[^a-zA-Z0-9_-]/g, "_")` was not (`imessage:any;-;alex.smith@x` and `imessage:any;-;alex_smith@x` shared one file). A key drawn only from `[a-z0-9:-]` keeps that legacy stem; anything else — including any key carrying an uppercase letter, because APFS and NTFS are case-insensitive by default — gets `<legacy stem>.<12 hex of sha256(key)>`, and since `.` is outside the legacy safe set the two families can never meet. So the "never moves" set is **keys drawn from `[a-z0-9:-]`**, not `dm:*`/`telegram:*` as a whole: `dm:shuai` and `telegram:-100123` keep their names, but a non-canonical identity key like `dm:shuai yuan` does move (and is migrated). Never build a transcript path from a key by hand — go through the store, or through the exported `transcriptFileStem` / `legacyTranscriptFileStem`.

Files written under the old scheme are migrated **lazily, on the first touch of a key** (`ensureTranscriptMigrated`, called from `get()`, under the `_transcripts.lock` advisory lock, and never throws on the message path). **The migration only ever renames — it never rewrites a transcript.** Ownership decides, compared case-folded because APFS and NTFS are: if no other key we know of maps to the same legacy stem, the active file, every archive and every sidecar are renamed over. If one does, the stem is AMBIGUOUS, and nothing is merged or guessed.

Four things that look like details and are not:

- **Legacy history that cannot be renamed into place is kept as a read-only sidecar.** When the destination name is already taken (a migration deferred by a held lock, while the message that triggered it appended under the new name), the legacy file is renamed once more — to `<stem>.legacy-<YYYYMMDD-HHmmss>.jsonl`, or `_archive_<stem>_<YYYY-MM>.legacy-<ts>.jsonl` for an archive. **It is searched and loaded, never appended to or rotated.** `loadTranscript`, `searchTranscript`, `transcriptCreatedAt` and `countRecentUserMessages` read sidecars (via `transcriptReadSet`); `append`, `getLastSeq`, rotation and `archivesForStem` must NOT — which is why `seq` uniqueness is only required within the active file and its rotation family. If you add a reader, add it to `transcriptReadSet`; if you add a writer, keep it on `transcriptPath` + `archivesForStem`.
- **A SIDECAR IS NOT NECESSARILY OLDER THAN THE FILE IT SITS BESIDE.** A re-key sidecars a transcript that ran *in parallel* with the one it lands next to, and an unmigrated process keeps appending to a legacy active file. So nothing may infer time order from the read set's filename order: with a sidecar present, `searchTranscript` has no cross-file early exit and sorts by record timestamp, `loadTranscript` sorts the tail it merged, and `transcriptCreatedAt` takes a minimum. `seq` bounds apply to the **active family only** (a sidecar is a separate run, so its numbers are not comparable) and are ignored for sidecar records. Without a sidecar on disk, the old ordered fast paths run unchanged — keep it that way, they are what every message pays for.
- **The migration's one move is `link` then `unlink`, never check-then-rename.** `existsSync(to)` + `renameSync` has a window another process's `append()` fits into, and the rename then overwrites a live transcript silently. `moveWithoutClobber` lets the kernel answer: EEXIST → the destination is taken → sidecar; same device+inode → our own interrupted move → just `unlink`. Only a filesystem that cannot hard-link falls back.
- **Quarantine and ledger repair are never "recorded and assumed".** The `.ambiguous-` marker says the decision was taken; the family is rescanned on every attempt and pre-decision files (newest record older than the marker's timestamp) are still parked. And one unreadable ROW in `_legacy_stems.json` defers only that stem — the row is carried verbatim into a `.corrupt-<ts>` sibling from the READ path and the good rows are kept; nothing is ever rebuilt from `{}` over a quarantined copy.
- **Ownership is read from `_legacy_stems.json`, not inferred, and an unreadable source is not an empty one.** The registry forgets keys — `cleanupExpired` drops an unlinked entry after 30 days while the transcript file stays, `clearSdkSessionId` deletes a metadata-only stub, `migrateSessionKey` re-keys in place — so all three write the key's legacy stem to that ledger *before* forgetting it, and refuse to forget when the write fails. `probeLegacyStemOwnership` reads the ledger, the registry and the session cache, and returns `unknown` (→ migration deferred, nothing adopted) when either file exists and will not parse. Any new path that removes a registry entry must record first, or a shared legacy file becomes silently adoptable again.
- **A key that KEEPS its legacy stem is checked too.** `dm:a:b` keeps `dm_a_b.jsonl` and `dm:a_b` takes a suffix, so the stable key is the one sitting on the shared file. It cannot leave the file where it is, so the family is parked as `<stem>.ambiguous-<ts>.jsonl` — unreachable, preserved, and itself the record that the decision was taken (without that marker, every restart would park the fresh history again).
- **A key is marked migrated only once the migration finished, and an unsettled key's answer is used.** An attempt that could not complete (transcript lock held by another process, EACCES, an unreadable ownership source) is retried, throttled by `TRANSCRIPT_MIGRATION_RETRY_MS`, and reported by `store.migrationStatus()` (`{settled, deferred, ambiguous, sidecars, orphans}` — the last three read off disk and logged on daemon start, the first two only meaningful once keys have been touched, so they are logged again five minutes in). While the probe's answer for a key is `shared` and its family is not parked yet, `get()` serves an EMPTY session and `searchTranscript` nothing: that key's own filename holds another session's history. `append` still writes there — the one window in which a known-shared file grows — and those records are parked with the family. Marking first and then refusing the both-exist case is what left a whole history on disk but unreachable from `loadTranscript` / `searchTranscript` / `transcriptCreatedAt` / `getLastSeq`.

### DM vs Group Detection

Use the helpers in `src/sessions/keys.ts` — don't re-parse keys by hand:
- `isDmSessionKey(key)` — true for `dm:` keys
- `parseRawSessionKey(key)` — `<channel>:<chatId>` → `{ channelName, chatId }` (undefined for `dm:` keys)
- `isGroupSessionKey(key)` — Telegram chatId starts with `-`; iMessage GUID contains `;+;`

### Live Sessions (SDK Integration)

`LiveSession` wraps the Claude Agent SDK `query()` call with an async generator for streaming multi-turn conversations. Key flow:
1. `getOrCreateLiveSession(key)` — reuses existing session or creates new one (with optional SDK session resume)
2. `session.send(text)` — sends a user message, returns the full assistant response
3. `runWithRetry(key, prompt)` — send with auto-retry on session errors (resets and retries once)

Each live session is a CLI child process (plus its stdio MCP servers), so idle ones are closed: `LiveSessionManager.reapIdleSessions` (config `liveSessionIdleTimeoutMs`, default 60 min, `0` disables) closes a session with no activity for that long and nothing going on — no turn in any phase, no live task (ambient watchers included), no task report due, no pending compact, no explicit MCP reconnect (`mcpReservations`), no SDK id the registry has not stored yet (`unpersistedLinks`), not already prompt-stale. The reaped session STAYS in the live-session map, marked closing, until its CLI child has actually exited (`LiveSession.whenClosed` waits on the child itself; bounded by `IDLE_REAP_CLOSE_WAIT_MS`, 10s, above the SDK's ~7s close-to-SIGKILL path `SDK_CLI_KILL_MS`), because that child may still append exit-time records to the transcript. Every path that looks the key up finds the entry and follows its usual rule: the next message waits (re-checking any rewind hold after every wake) and then resumes from disk, a `/rewind` waits before its snapshot, a compact reservation is refused (`session-closing`, retried by the next nudge), `closeLiveSession` and the prompt-change sweep leave it alone. The sweep timer stops once no session is alive (dead entries stay in the map) and re-arms with the next one built.

The prompt-change sweep retires a live session when the *identity* prompt changes (`buildIdentityPrompt()`: SOUL, AGENT, IDENTITY, HARNESS and the home note). The MEMORY.md index and the people roster are also in the system prompt, but the agent edits them during ordinary turns, so they are not hashed. Instead a session keeps the lines its prompt was built from, handed over by the build itself (`buildSystemPrompt({ onContext })` → `SessionContext.onPromptContext`, audience-filtered and cut at 200 lines, never a second read), and before each turn `LiveSessionManager.takePromptContextNote` re-reads them strictly (`promptContextSnapshot({ strict })`: only ENOENT counts as missing, `loadPeople({ strict })` throws on an unreadable directory or record) and compares (`classifyPromptContextChange`, `src/workspace/prompt-context-diff.ts`). ONLY a small change of whole lines gets a `<tomo-event type="memory" name="changed">` note: lines added or removed, at most `MAX_NOTED_LINES` (10) lines and `MAX_NOTED_CHARS` (2000) characters in all, each told with the full heading path it sits under, every kept line in the same order, no heading line touched. Anything else (a reorder, a heading, more lines) retires the session the old way, at its next idle boundary (at once when idle, so the turn runs on a fresh session); so does a failed strict read, but only when the lenient read a rebuilt prompt would use differs, so a persistently unreadable record does not retire it every turn. The note never enters the durable pending-notes store (replayed after a restart it would describe a prompt the new session does not have): the TurnRunner takes it as a ticket (`TurnRunnerDeps.takePromptContextNote`), puts its prefix first, carries the ticket on `RunWithRetryRequest.contextNote`, and settles it (`told` only when the turn ran to its normal result and was not stopped by the owner; otherwise the session's snapshot is rolled back and the next turn compares again). Only a turn of the session's own audience (`isOwnAudienceTurn`) takes a note: a summoned group's turn on a `dm:` session, or a mixed batch, gets none and leaves the snapshot alone, so private index lines and private people wait for the owner's next turn. At most one note is in flight per session (a steered turn gets none), and a prompt that lands on a different session than its ticket names (an identity change retired it on the way, a session-error retry) has the note stripped (`promptForSession`). Retiring on every memory edit threw away the session and its warm prompt cache for a one-line index change.

SDK session IDs are persisted in the session registry so conversations survive daemon restarts. Every mutator goes through the private `mutateRegistry(op, mode, fn)`, which holds an advisory cross-process lock (`_sessions.json.lock`, `src/file-lock.ts`) for the whole load→mutate→save and forces a fresh read inside it (bypassing the stat cache) — the daemon and a short-lived CLI (`tomo sessions clear`, identity migration) write the same file, and publishing a whole-snapshot copy read before the other's write is a lost update no atomic rename can prevent. A lock that cannot be taken follows the same split as an unreadable file: link-changing mutators throw, bookkeeping logs once and skips. The stat cache keys on the file's identity (device+inode, size, nanosecond mtime/ctime; every writer publishes by atomic rename, so another process's write is a new inode), and is only recorded for a file this process read or wrote while holding the lock. The per-message bookkeeping mutators (`setReplyTarget`, `setChatTitle`, `addParticipant`) first check the active entry of the latest published file (that cache, re-read on any identity change) and return without the lock when nothing would change; a no-op never writes, so answering before an in-progress writer publishes is just the order where the message landed first. A link change whose save threw re-reads the file, so that fast path never answers from an unsaved change. A registry that cannot be read is not an empty one: `loadRegistry()` separates ENOENT (legitimately empty) from a read/parse failure, keeps the last known-good state in memory, and refuses to persist until a later load succeeds — so one unreadable instant can no longer be persisted as `{version:1,sessions:[]}`. How it refuses depends on the mutator: bookkeeping (`updateStats`, `touchSession`, `setChatTitle`, `addParticipant`, `setReplyTarget`) skips silently because it runs on the inbound and turn-completion paths where a throw drops a message or fails a good turn; link-changing (`setSdkSessionId`, `clearSdkSessionId`, `retireSdkSessionId`, `migrateSessionKey`) throws `SessionRegistryReadError`. Both guard *before* mutating, so nothing is left applied-but-unsaved. Every registry write is fsynced (`writeFileAtomicSync` loops until every byte is written), and every link change that saved also rewrites `_sessions.json.bak`; a backup write that failed is retried after the next save of any kind, and each start rewrites a backup that is missing or does not hold the registry's links (once any entry is linked). A backup without a `sessions` array is never recovered from. A process that holds no entries yet and finds the registry 0-byte or unparseable (a restart after power loss) recovers from `.bak`, keeping the bad file as `_sessions.json.corrupt-<ts>` (a second name, never a rename: the primary path must exist until the recovered copy replaces it, because a missing registry reads as empty); with no usable `.bak`, a 0-byte file in a directory with history (transcripts or a `.bak`) is refused, never read as a fresh install. A process that already holds entries never recovers over the file — it refuses as before; so does a read-only reader (the web process), which fails closed and leaves recovery to the daemon's next start. An I/O read error never triggers recovery.

`LiveSession.stop()` is the owner's Stop (web UI): the SDK's `interrupt()`, a SOFT stop. The CLI ends the turn at its next checkpoint and still yields a `result` (error-shaped), which is settled as a clean end for the request that was running when Stop was pressed: no failure, no error notice, the session and its background tasks stay. It is not `LiveSession.interrupt(err)`, which fails the turn and closes the session (`/rewind`). The owner's web session declares `perTaskStopAffordance` (`sdk-options.ts`), so that interrupt spares background agents; ONE task is stopped with `LiveSession.stopTask`, and a foreground one is moved to the background with `LiveSession.backgroundTask` (web task view, owner conversation only, `WebChannel.taskAction`). A stopped turn is NOT a finished one: the session marks the stopped request's own `ReplyContext.stopped` (never a flag on the session, which a compact reload closes before the runner looks), the runner calls `TurnSpec.onStopped`, and the cron scheduler settles such a run exactly like one cut short by shutdown (one-shot parked, recurring `interrupted`, owner told), never `ok`.

With config `steering` (default on), user messages that arrive mid-turn bypass the per-session queue via `session.steer(text)` — they either merge into the in-flight turn or are promoted to their own follow-up turn. Details (STEER_MERGED sentinel, replay detection, idle-wait) live in `src/agent/turn-runner.ts` and `src/agent/live-session.ts`; set `steering: false` or `TOMO_STEERING=false` to keep mid-turn messages queued.

### Message Flow

`/rewind [N]` is an owner-DM command executed inside the shared session queue without a model call. It closes the idle SDK child, uses the SDK's active-chain reader and fork API to branch before N recorded human messages, then atomically swaps the registry link with `replaceSdkSessionId` (expected-ID check). The original SDK file and Tomo transcript are preserved; the old link follows the usual 30-day retention. Tool results, harness turns, summaries, and entries without human provenance do not count. Never rewrite the source JSONL or rewind files. Refuse corrupt/changing snapshots and active autonomous turns. Whole-file reads are asynchronous; the final pre-publish check uses file identity, size, and nanosecond modification/change times without yielding before the link swap. An unpublished fork is deleted after validation, shutdown, or link-publication failure; cleanup failures are logged without masking the original error. Only numeric API errors and the known nonnumeric safeguard prefix are classified as error text. Safeguard API errors are delivered once with recovery guidance and are not queued back into model context as pending error notes.

1. Channel receives message → `agent.enqueueMessage()` (serialized per session key)
2. `handleMessage()` — admission check, owner resolution, timestamp injection
3. `runWithRetry()` → `LiveSession.send()` → SDK query; each completed assistant content block ships to the channel as the SDK closes it (no partial-token streaming — `includePartialMessages` stays off)
4. After the `result` event the joined response drives only the transcript, logging, and silence/error policy (`src/agent/turn-runner.ts`, `src/agent/delivery-pipeline.ts`)

### Durable Inbox

`src/agent/durable-inbox.ts` (config `inbox`, default on) is an append-only, fsynced JSONL log at `~/.tomo/data/inbox.jsonl`. `enqueueMessage` writes a `recv` record AFTER admission (allowlist, /pause, pasted OAuth callbacks, the group secret never reach disk) and BEFORE returning custody to the channel — the `true` that makes imsg commit its cursor. Dedup is on `(channel, chatId, message id)`; a duplicate is acknowledged and not dispatched. `processInboundItems` marks items `start` before the turn and `done` in a `finally`; deliberate drops are `done` too. On `start()`, after channels are up, `replayInbox()` re-dispatches `received` records through the same `dispatchInbound` path (so batching, settle and steering behave as live), notes `started` ones to the session instead of re-running them (the turn may already have acted), and records anything older than `inboxReplayMaxAgeMinutes` (or whose channel is gone) with `INBOX_STALE_NOT_PROCESSED`. Shutdown and the crash handler skip recording items still pending in the inbox, since the next start replays them. Web requests are never persisted (their outlet is a live HTTP request). Attachment bytes are never written — only `savedPath`, reloaded on replay. The log is compacted on load and every N appends, keeping live records plus `seen` tombstones (7 days / 10k); unreadable lines go to a `.corrupt-<ts>` sibling, and an unreadable log disables compaction rather than rewriting it from nothing. Agent test suites run with `inbox: false` (mockConfig) unless they opt in.

### Harness Message Envelope

All harness-composed messages (cron, heartbeats, nudges, summons, delegate requests) are wrapped in a `<tomo-event type=... name=... ts=...>` envelope by `formatTomoEvent()` (`src/tomo-event.ts`) — the single composer; never hand-roll `System:` strings. Bodies are injection-escaped so user-controlled text can't close the envelope early. Consumers must tolerate BOTH the envelope and the legacy `System:` / `[System: ...]` formats — old transcripts are never migrated. Outbound, `src/agent/scaffold-filter.ts` strips training-scaffold leaks before text reaches a channel, and `src/agent/inbound-markers.ts` catches the mirror-image failure: the model WRITING one of the harness's own inbound markers (`[imessage · …]`, `[group "X"] Sender:`, `<tomo-event …>`, `System: …`) into its reply and then answering it as if a person had typed it. That one is **marked, not truncated** — the block ships whole with `FABRICATED_MARKER_NOTICE` prepended to the DELIVERED copy only; the transcript and every classification keep the model's verbatim words. Only lines that *start* with a shape and sit outside a ``` / ~~~ code fence count (fences matched per CommonMark on both ends; any line-break convention; leading invisibles count as indentation), so discussing or pasting these markers is safe. Both outlets for model-authored text run it — reply blocks (`LiveSession.shipBlock`) and `send_message` direct mode (`ProactiveSendService.sendToSession`); delegate mode goes through a real turn and needs nothing extra. It also owns `formatInboundStamp` / `formatGroupTag`, the formatters the ingress path uses to build those markers in the first place, so detector and producer cannot drift.

### Sending Notifications (No Agent Query)

`agent.sendNotification(text)` sends a direct channel message without invoking Claude:
1. Tries the owner's `dm:` session via OwnerRouter
2. Falls back to first non-group session key from the registry
3. Uses `privateReplyTargetFromSessionKey()` (`src/sessions/keys.ts`) which excludes groups

Use this for system-level notifications (version updates, errors) that don't need AI processing.

### People Registry (Group Sender Recognition)

Person records live at `~/.tomo/workspace/memory/people/*.md` (DM-only records under `memory/private/people/`) — frontmatter holds `name`, `aliases`, per-channel handles, an optional `timezone`; freeform notes below. Resolution is harness-side and deterministic (`src/people.ts`): channels attach a stable `senderId` to every message, group transcript lines are annotated inline (`ali ✨ (Alice Example): ...`), and handles auto-bind the first time a sender's display name unambiguously matches an unbound public record. The agent maintains records via `list_people` / `upsert_person` MCP tools; a roster (names + aliases + time zone) is injected into every system prompt. `timezone` is an IANA REGION identifier (`src/timezone.ts` validates it and drops unusable values with a single log line; fixed offsets, the `Etc/` namespace and the legacy all-caps aliases are refused because they carry no DST rules). `list_people` reports a stored value that fails validation as `timezone_invalid`, so the model can repair the record it is otherwise told to ignore. It reaches the model twice, and the split is deliberate: the CACHED system prompt (roster, group participants) carries the identifier only, never a clock reading, while the per-message inbound stamp — which varies anyway — carries the sender's live local time (`[imessage · Wed 09/02 20:50 PDT · sender 09/03 12:50 GMT+9]`), omitted when the sender has no time zone or reads the same clock as the host. Private records never enter group flows — excluded from group prompts, group-session tools, and file reads (private-memory guard hook), even when a summon routes group messages into a `dm:` session. The bar is decided in one place (`privateMemoryBarFor`, `src/agent/private-memory-guard.ts`, re-exported from `permissions.ts`) and enforced on both sides of the turn: inbound, the PreToolUse hook denies the file/search tools by path and **sandboxes Bash** — the command is rewritten via the hook's `updatedInput` to run under a `sandbox-exec` profile that denies `memory/private/` (reads and writes) in the kernel (`src/agent/bash-sandbox.ts`), because no filter over command text can scope a shell away from a directory (`node -e` and friends assemble a path the token scan never sees) but `open(2)` on the resolved path can. The profile is passed INLINE (`sandbox-exec -p`), never as a file: an earlier revision wrote it to `~/.tomo/data/` and memoized the path, which put the policy in a file the sandboxed shell could overwrite under `(allow default)` — two commands in one turn were enough to escape. The deny subpath is computed with `realpathSync.native` — `realpath(3)`, not node's JS reimplementation, which folds `..` lexically BEFORE following links and so disagrees with `open(2)` whenever a `..` sits behind a symlink (`realpathSync("/tmp/..")` is `/`, `realpathSync.native("/tmp/..")` is `/private`); a path whose real location cannot be established (a dangling symlink, a loop, a `..` in the spelling) fails closed rather than denying the wrong directory. Registering the guard last is NOT sufficient on its own: the CLI keeps the last `updatedInput` from any PreToolUse hook and project/plugin hooks reach it through the CLI's own merge, so `foreignPreToolUseHookSource` scans the loaded settings files (derived from `SDK_SETTING_SOURCES`, `src/agent/setting-sources.ts`) and the mounted plugin dirs on every barred Bash call and withholds the shell when any PreToolUse hook is present. `--` terminates the inner shell's option list so a dash-leading command still runs. If `sandbox-exec` is missing the fallback is the old outright deny, never an unsandboxed shell. It is also registered LAST among our own PreToolUse producers, which is necessary but not sufficient for the same reason. Outbound, a `MEDIA:` attachment is a read, so `send_message` is refused at the hook and reply delivery drops private paths before the send (`isPrivateAttachmentPath`, `blockPrivateMedia` on the delivery pipeline). The same bar closes Tomo's own state, `<tomoHome>/data/` plus the sessions dir (`harnessDataDirs`): the file tools and attachments are refused there (`isHarnessDataAccess`), any Grep/Glob/LS whose root (`~`-expanded, realpath'd) is at, inside or ABOVE a barred dir (memory/private/ or data/) is refused outright without judging its pattern (`barredSearch`), and the Bash profile denies it for reads AND writes. It holds every conversation (transcripts, inbox, the usage ledger), so a group never reads it directly; what a group needs from it comes through harness tools.

### System Prompt

Built by `workspace/index.ts` from layered markdown files:
- `SOUL.md` — personality and values
- `AGENT.md` — operating rules
- `IDENTITY.md` — name and quirks
- Memory system — injected from `~/.tomo/workspace/memory/`
- Harness instructions — NO_REPLY, MEDIA: tags, formatting rules
- Owner DM only: the home note, and with `subsessions.enabled` the `DELEGATION_NOTE` (when to work in the turn, use an Agent subagent, or `task_spawn`; task_spawn's own description says only how to use it). Groups and task sessions never get it; the note itself says it holds only in a turn the owner wrote privately, since a summoned group's turn runs on the DM session (the prompt is per session, the audience per turn) and task_spawn refuses it.

Changes to workspace files take effect on next message (no restart needed) — the prompt is rebuilt on each new LiveSession.

**The owner's `dm:` session has two prompt variants** (`buildSystemPrompt({ shared })`): the full one, and the SHARED one, which leaves out the MEMORY.md lines that link into `private/` and the private people records (the same filter as a group prompt) and says so (`SHARED_PRIVATE_MEMORY_NOTE`); everything else is the DM prompt. A live session keeps the variant it was built with (`LiveSessionManager.sharedPrompt`), so the variant is chosen per TURN, when it is dispatched (`sessionForTurn` ← `deps.promptVariant` = `Agent.promptVariantFor`), never when the message was queued:

| Turn on the `dm:` session | Variant |
|---|---|
| The owner's private message (any channel, web), no summon | full |
| The owner's private message while a group is summoned in | shared (preferred) |
| A summoned group's message; a batch mixing the owner with a group; any turn overlapping one | shared (required) |
| A group's delegate, cron job or restart notice handed to the session | shared (required) |
| The owner's own cron job, heartbeat, rollup or other background turn | as the owner's message: full, or shared (preferred) during a summon |
| A delegate the owner's own private turn asked for | as the owner's message |

Group sessions and sub-sessions have one prompt each and are never reloaded for this. *Required* is `!isOwnAudienceTurn(key)`, the same fail-closed reading the session-scoped tools use; *preferred* is `OwnerRouter.hasActiveSummonInto(key)`, which also runs the summon's lazy expiry check, so a session goes back to the full prompt on the owner's first turn after a summon ends, with no event. When the live session has the other variant, it is closed and resumed from disk first (`closeReaped`: the resume waits for the old CLI to exit), but only when nothing would be cut (`variantSwitchBlocker`: the idle reaper's conditions). NOT `retireWhenIdle`, which waits for the queue to empty and would let the waiting turn run on the old prompt. When it cannot be closed: a *preferred* turn runs on the session as it is; a *required* one waits at the head of the session queue up to `PROMPT_VARIANT_SWITCH_WAIT_MS` (5 min) and is then refused (`SharedPromptUnavailableError`) without a model call: the group gets one fixed line and the owner a notice (`Agent.answerSharedPromptUnavailable`). Background work is never stopped for a variant. A steer never reloads a session: a group's message is kept out of a running turn on the full prompt at ingress (`steerNeedsSharedPrompt` → the batcher's `canSteerIntoSession`) and declined again at injection (`SteerDeclinedError`, which `processInboundItems` re-queues as its own turn, transcript record and inbox id kept). A session on the shared variant takes no memory-change note and is not retired for one. Each reload restarts the CLI and its MCP servers and misses the prompt cache for the whole conversation (the system prompt leads it). While a group is summoned in, the rollup runner defers the session's rollups without arming their cooldown.

The workspace files are copied once (`tomo init`; CONTINUITY.md at start when missing) and are the owner's from then on, so they are never updated in place (only `tomo init --force` overwrites them). Keep them to personality and personal habits; anything about how Tomo works (tools, routing, delivery, summoning, heartbeats) goes in code-side prompts, events or tool descriptions (`tests/workspace-defaults.test.ts`).

### Daemon Lifecycle

`tomo start` defaults to background (spawns detached child with `--foreground`). On macOS, `tomo config` can enable launchd autostart (LaunchAgent plist at `~/Library/LaunchAgents/ai.tomo.plist`).

`startForeground()` in `cli/start.ts` is the real entry point — it:
1. Creates Agent, adds channels
2. Starts CronScheduler, ContinuityRunner, VersionChecker
3. Writes PID file
4. Handles SIGINT/SIGTERM for clean shutdown

### Cron System

Users ask Tomo to schedule things via chat. The agent CRUDs jobs with the `schedule_create` / `schedule_list` / `schedule_remove` MCP tools (`src/mcp/cron-tools.ts`), backed by the `cron_jobs` table in `~/.tomo/data/tomo.db` (the `tomo cron` CLI and the web Study are parallel surfaces on the same store). The `CronScheduler` polls every 30s and fires due jobs via `agent.handleCronMessage()`, which delivers the response through the appropriate channel. A run is recorded on disk *before* it is dispatched (`markStarted`), so a daemon that restarts mid-run can tell "was running" from "never ran": on start, `recoverInterrupted()` settles those runs before any due-scan, and a graceful shutdown that cuts a cron turn short settles it the same way (`markInterruptedByShutdown`). An interrupted run is never re-run automatically: a one-shot is parked (`lastStatus: "interrupted"`, disabled) and the owner is asked whether to run it again, a recurring job records `interrupted`, moves to its next normal slot and the owner is told once (`interruptNotice`). `schedule_enable` is how a parked job is brought back. Every store change is one SQLite write transaction (`BEGIN IMMEDIATE`: read the jobs, change them, write back the changed rows), so the daemon, a `tomo cron` CLI and the web process can never interleave a read-modify-write and a stale snapshot cannot erase a dispatch record. The old `data/cron/jobs.json` is imported once by the daemon at start (`importLegacyCronJobs`; renamed `.migrated-<ts>`, replaced by a placeholder an older Tomo refuses to read as "no jobs"); while a real jobs file sits there un-imported (an older Tomo or `tomo db export cron` wrote it) every store call refuses. An unreadable store throws rather than reading as empty. A recurring (`every`) interval is bounded by `MIN_EVERY_MS` (30s — equal to the poll, since a job cannot fire more often than the scan that dispatches it) and `MAX_EVERY_MS` (366 days, which also catches intervals that multiply past `Number.MAX_SAFE_INTEGER`); the bound is enforced in `unschedulableReason` for the creation surfaces, in `CronStore.add` for anything that skipped them, and on import, where a job in the old file with a bad interval is imported disabled (warn logged) instead of firing or failing the whole import.

### Sub-sessions

A long task runs in its own SDK session under `task:<id>` (`s1`, `s2`…, ids global across scopes). `sessionKind(key)` (`src/sessions/keys.ts`) is `owner-dm | group | task | raw`; a task key is not a DM, not a group and has no chat (no reply target, no `send_message` target). The task's OWNING scope lives only in its record (`parentKey`, today always the owner's `dm:` key): delivery, notices, the report and the privacy bar are all resolved from it, an unknown task counting as a group (fail closed).

- **The table is the truth.** `data/subsessions.json` holds the lifecycle (`queued | active | waiting(owner|external) | finished | cancelled | failed | archived`); whether a turn is in flight is runtime state, never persisted. Every status change goes through `SubsessionStore.transition` (compare-and-set under the lock, table in `state-machine.ts`, the last 50 changes kept on the record). Strict mode (tests) throws on an illegal transition; production logs and refuses. A driver that throws is tried again by the `SETTLE_RETRY_MS` timer, never re-kicked at once (a failure that persists, like a table that reads but will not write, would loop before any timer or I/O runs).
- **One scheduler.** Every autonomous start (spawn, cron check-back, background report on a task waiting on something external, the owning session's own note to one, resume after a restart) lands in `queued` and only `schedule()` makes it `active`, under `maxRunning`. A relay that carries the owner's own messages is never queued; it wakes a waiting task. The owning session's note alone is the `note` event: it queues a `waiting(external)` task. To a task the harness paused at one of its limits (`pausedBy.kind` in `MAIN_RELEASABLE_PAUSES`: `quota`, `active_hours_cap`, `no_progress`, `turns_failing`; set by `pause()`, dropped by the store on any move out of `waiting(owner)` and when a question replaces the pause) it is the `release` event (`releaseByMain` → `queued`, `released` on the result): the pause is there so the owner knows, and the owning session speaks for them. The record says who lifted it (the transition's reason, and a line in `updates`), the input stays `from: "main"`, a cap pause counts from the release, and a quota pause leaves `quotaPass`. To any other `waiting(owner)` task (a question, a stop the owner made, a self-restart, a wait that recorded nothing: fail closed) it is not a transition: `relay()` appends it held (`heldThrough`) and goes with the owner's wake (`relay` → `held: "answer"` with a recorded question, else `"paused"`). Nothing autonomous wakes `waiting(owner)`: a cron check-back that fires then is a legal no-op transition (`cron_wake` → same) that keeps the check-back as held input (deduped per job), never a failed fire.
- **Unattended, so fenced.** A task session loads no external MCP server and no claude.ai connector (`sdk-options.ts`, for every `task:` key whatever its scope; `buildExternalMcpServers` builds nothing for it), and runs with `strictMcpConfig` and every plugin `skipMcpDiscovery` (nothing the CLI discovers itself); its tools are the internal allowlist. A turn the task gives itself (no owner input in it: a continue, a check-back, its start) first passes `gateOwnTurn`: past `maxActiveHours` of active time since the owner's last word to it (`activeAtOwnerInputMs`), or with the fuller of the 5-hour and weekly (all models) windows at `subsessions.quotaPauseAtPct` (default `QUOTA_PAUSE_PERCENT`, 85) or more (`QuotaGateReader` → `readQuotaGateReading` over `usage/limits.ndjson`: an oauth read with no 5-hour window reads it as 0, so such an account is gated on the week; a window present with no percentage leaves the older reading standing; `drive` first awaits `freshenQuota` → `ensureFresh`: when the newest complete oauth sample is over 30 min old it takes one `fetchUsage` (joining one in flight) and waits at most `QUOTA_REFRESH_WAIT_MS` (15 s), throttled to one per 30 min worked or not, a read unsettled after `QUOTA_REFRESH_TIMEOUT_MS` (60 s) counting as failed; samples older than `QUOTA_GATE_SAMPLE_MAX_AGE_MS` (6 h) do not count (none recent → gate open, one warn); wired by `cli/start.ts` via `Agent.setQuotaRefresh`, never in tests; unreadable → the turn runs, logged), it pauses to `waiting(owner)` with one notice naming the window and its share. A go-ahead after a quota pause (the owner's own input to the paused task, or the owning session's `release`) sets `quotaPass` on the record (`{ until }`: `pausedBy.resetsAt`, the fuller window's reset time as the pause read it, else `QUOTA_PASS_FALLBACK_MS`, an hour, from the go-ahead): the gate does not pause that task for quota again, on either window, before `until`; the store drops it when the task finishes or ends (without it the first continue after the go-ahead paused again at once). A turn carrying the owner's input (`from: "owner"`) always runs. Owner input is only what the owner wrote: a `/s` message, a web panel message, or a relay with the owner's own messages attached (`task_message` `attach_owner_message`: the harness copies the messages of the owner's own live turn, `TurnAudienceRegistry.ownerMessages` → `Agent.turnOwnerMessages`, `[]` on any group or summoned turn). The owning session's own note is `from: "main"`: it answers no `task_ask` and is never the owner's yes to anything; outside a `release` it resets no cap and passes no gate. In the relay text the owner's lines start with `> ` and the note's with `| `, so a note cannot pass for their words. Every input gets its origin when it is created (`appendInput` requires one: `owner`, `main`, or `harness` for a check-back, a continue, a background report); only `from: "owner"` is the owner's, never guessed from the text, and an input read without one is `harness` (fail closed). An owner input is written with `checked: true`; one stored `from: "owner"` without it predates these origins, when every relay (the main session's notes too) was stored as the owner's, so it is read as `main`, unless it is an owner message (`OWNER_MESSAGE_MARKER`, an envelope only the harness writes). A note alone (no owner messages attached) to a `waiting(owner)` task lifts a harness-limit pause (above) and is otherwise held for the owner's wake (`held: "answer"` with a recorded question, `"paused"` otherwise, including a wait that recorded nothing). A pause that cannot be written runs no turn and waits for the settle retry timer.
- **Turns are silent.** A task turn runs through the TurnRunner with delivery suppressed; a task speaks only through `task_reply` (an answer when its turn carries the owner's own words, by stored origin: a message, or a relay with theirs attached; else unprompted news) / `task_ask` and reports with `task_finish` (a pinned `subsession-report` note to the owning session plus a silent wake there).
- **Owner messages go via the owning session (`subsessions.ownerMessages`, default `via-main`).** `speak` routes all three (and the fallback answer): a PINNED `subsession-message` note (`formatMessageNote`: task id/title, the words in full, what the session should do; named `id:kind:<highest input seq the turn answers>:sha256(words)`: the same name again adds nothing while that note is unread, nor does an unread note of the same words from an earlier attempt of the turn (its seq among the inputs carried again, at most `seenThrough`) when newer input joined the retry, while the same words answering another message are another note (each unread note stands for one message per turn, `notesUsed`). The sweep keeps a task (archive and forget) while a message note of its own is unread: recovery finds the session to wake through the records. Past that, delivery is at-least-once like every task send: a note from a retried turn (`PlannedTurn.retry`: inputs that may have been seen, a resume, or a last turn that failed or whose result could not be written, `lastTurnFailed`) says it may repeat what the session already read, and the session that tells the owner is the dedup point. A panel answer is idempotent across a retry: `sent.answers` keeps the highest input seq its turn carried; the same answer that an earlier attempt wrote while carrying inputs this turn carries again (seq at least the first pending, at most `seenThrough`) is not shown again, each such entry matched once per turn (`panelRepeatsUsed`), so the same words answering a newer message still show. Note names are read from the outer envelope only (`messageNoteNameOf`), never from a body that quotes a tag) on the record's `parentKey` (a group-owned task's goes to that group, never the DM; a DM note is owner-audience), plus `Agent.messageWake` (merged per session, runs only while such a note is unread, not held at the quota pause; a turn that leaves one unread retries `MESSAGE_WAKE_RETRY_MS`, up to `MESSAGE_WAKE_RETRY_MAX` times). The task is told "handed over" only once the note is on disk; a failed write is withdrawn from memory (`PendingNotesQueue.withdrawNote`) and fails like a failed send (`markDelivery`: the turn keeps its inputs). Restart recovery re-owes the wake for any parent with an unread one. The record logs it (`sent.via = "main"`, conversation entry `noted`, which the mirror skips). `task_ask` (`askViaMain`) writes the note and makes the guarded `ask` transition with no await between; a refused wait (input pending) takes the note back (`withdrawn`). The wait stores `askViaMain` (text, note name; the store drops it on any transition out of waiting(owner)); a relay (`task_message`) to a task holding it is formatted as the owner's answer quoting the question, and wakes it. The relay that answers takes an unread copy of the question back; any other end of that wait (an owner message, cancel, a new question, restart recovery), seen in the service's `transition` wrapper, retracts the question: its note is withdrawn if unread, else a "no longer waits" note follows, with a wake. A question note stands only while its task's `askViaMain.note` names it: at start, recovery takes back any other left on disk (a withdrawal whose write failed). Exception: a `reply`/`fallback` in a turn whose owner messages all came from the web panel (mixed with one from the phone, or with a relay carrying the owner's words: via main; every `task_reply` of such a turn stays in the panel) (`ownerMessage(..., { source: "panel" })`, kept on the input) stays in the panel (`sent.via = "panel"`, an unnoted conversation entry the mirror shows), unless it carries a `MEDIA:` line (the panel shows text only). `direct` is the old path below: `sendOut` to the owner's chat with the `[s3 · title]` prefix and `replyMap`; its `task_ask` also stores the wait (`askViaMain` with `direct: true`, no note, nothing retracted at the main session), so a main-session note alone is held for the owner's answer there too. Whether a turn answers the owner (the fallback answer) is read from each input's stored origin (`from: "owner"`), never from text a note could quote.
- **Owner addressing (`address.ts`, `commands.ts`).** In the owner's own DM (not web, not a group), `Agent.enqueueMessage` parses `/s` before the router: a command (`/s`, `/s s3`, exact `stop`/`start`/`model <alias>`) is answered with no model call; `/s s3 <text>`, or a reply/reaction to a message whose provider id is in the task's `replyMap`, is resolved to `task:<id>` and, after the durable inbox `recv`, `dispatchInbound` hands it to `SubsessionService.ownerMessage` (dedup on `ownerMessageIds`, a `subsession-owner-message` event, wakes `waiting(owner)`). A task that is unknown, ended or unreadable sends the message to the owner session with a note instead. The task answers with `task_reply` and asks with `task_ask` (→ `waiting(owner)`); an owner-message turn that said nothing gets its suppressed text as a `[s3 · …]` fallback, and one with no text at all keeps the message for the next turn (never used up unanswered). A task that fails hands the owner's `/s` messages back with the rest (`subsession-handback`, below). `/s start` on a task the registry hold is keeping back says so (`isHeld`). Channel `send()` returns `SendResult.messageIds` so the prefix-carrying messages are recorded; `inbound-markers.ts` treats a model-written `[s3 · ` line as a fabricated marker (the harness prefix is skipped via `harnessPrefix`). Telegram lets `/s` past its slash-command filter (`looksLikeTaskAddress`). A reply to a task message still being sent is taken into the inbox first, then matched again after up to `TASK_SEND_SETTLE_MS` (inbox replay matches it the same way); still unmatched, it stays with the owner session, which is asked to resend it with `/s <id>` (the ids of the tasks that were sending ride on the message, `IncomingMessage.taskSendsInFlight`, so the inbox replay warns the same way). A message to a task is exempt from the inbox replay window: it waits in the task's own queue (deduped on `ownerMessageIds`); only one whose channel is gone is recorded in the owner's transcript as not processed, plus a pinned note to the owner's session (the record is closed once that note is on disk; one the task already has is closed quietly). An owner's `/s start` passes the cap and quota gate for its first turn (also when the registry hold made it owed, and through a `/compact` ahead of it); a `/s` message is owner input, so it always runs, resets the `maxActiveHours` count, and is handed back if the task fails. A fallback answer that cannot be sent keeps the turn's inputs for the next turn; a finished task gives up after two failed turns and hands them to the owning session as a `subsession-unanswered` note plus a wake (the task keeps them for the owner's next message).
- **Following along.** `/s start` and owner messages never wait for a slot (an owner message to a queued task starts it; `schedule()` reads that from the table, a queued task holding a `subsession-owner-message` input starts past the cap, so a failed start or a restart cannot leave it waiting for a slot). Active time is banked only up to `activeSeenAt` (set when a task becomes active and when a turn's result is written, plus a heartbeat every minute while a turn runs; restart recovery banks it before anything else), so downtime after a crash never counts toward `maxActiveHours`. The task record is its own card: no todo is made for it (an old record's `todoId` is dropped on read, an old config's `subsessions.todos` ignored). A report that needs the owner to act carries `task_finish`'s `owner_action` as `ownerAction`; `needsOwner(record)` (finished AND an action) is the one read of it: the Tasks rail and `/s` show "Needs you", the sweep never archives it, and `/s stop` and `task_cancel` refuse it (pointing to done), until `markDone` (`/s <id> done`, the owning session's `task_done`, the web Tasks rail's Done button, which sends the report seq the page showed) (that report's ask only: `task_done` carries the report seq its note named, and `/s <id> done <n>` the one `/s <id>` showed, a bare `done` report 1, so a newer report's ask is never cleared by an answer to an older one) clears it or the next `task_finish` sets it afresh; a reopen hides it without clearing it. Old todos the link made are dropped at start from the table as read, before recovery or the sweep forgets a task (`legacy-todos.ts`, via `recoverAtStartup`'s `onTableRead`): only the item the record names (`legacyTodoId`, an old record's `todoId`; else its exact title) and still word for word as the link left it (never snoozed, a waiting_on/next pair it wrote; one the owner snoozed or handed off, or anything that only looks like the link's, stays on the list), a finished task's open item moved onto the record as its `ownerAction` ("Read sN's result") first, and until that pass is complete the sweep archives or forgets no record. Owner↔task words go into the record's `conversation`; the owning session is shown what it has not seen (`mirrorSeenSeq`) as a `subsession-activity` "mirror" prefix, taken like the memory note (a `MirrorTicket` on the TurnRunner, advanced only by a turn that ran to its result, only on an own-audience turn, one in flight). Mode `turn` adds one merged silent wake after a round with unseen words the owner wrote to the task (what the task said alone waits for the session's next turn), and none while the quota gate is at its pause (asked when queued and when it runs). Nothing about it is durable; the old direct-send/owner-wrote pending notes are not written for task traffic.
- **Inputs are append-only, at-least-once, never dropped.** A relay, message or check-back is appended to `pendingInput` with its own `seq` (`appendInput`). A turn only READS them and remembers, in memory, the highest seq it carried; nothing is written before the turn. The one write that records the turn's result removes the inputs it carried, atomically; a failed turn, or a completed one whose message to the owner could not be delivered (a failed `task_reply` / `task_ask`, or a fallback answer, is recorded as part of the turn's result; every send goes through `sendOut`: one that fails or throws marks that text undelivered, only a later send of the SAME text that goes out clears it (other words answer something else; the next turn is shown the lost text), and a turn that carried no input keeps nothing), keeps them and raises `seenThrough` ("may have been seen"), so the next turn gets them again behind a `subsession-redelivery` note. A finished task whose answer keeps failing, or that the owner stopped, never deletes them either: they are held (`heldThrough`, through what that turn carried; input that arrived during it still gets a turn) and come back with the owner's next message. A "continue" owed also leaves only with that write, and an active task keeps one until a transition out of active is WRITTEN, so a pause, wait or count that throws after the result leaves it with a turn owed. A result that cannot be written blocks the task's turns until a retry timer (`SETTLE_RETRY_MS`). There are no dispatch markers. The 7-day archive skips a finished task with input pending or held, so it can still be woken to answer, and the sweep never archives or forgets a task whose report note is still unread (a note is named by task id and report seq, `s3#2`, so a later report is never mistaken for an earlier unread one). The list is not trimmed: at `PENDING_INPUT_MAX` new input is refused (a guard on `transition`), and the caller or the owner is told; input held for a `waiting(owner)` task (a main-session note, a check-back) stops `PENDING_INPUT_OWNER_RESERVE` short, and the owner's own input to a `waiting(owner)` task is taken even past the limit, since only it wakes the task. Every wait (check-back, no-progress pause) is guarded under the lock on "no input pending": input that lands during or right after a turn gets a turn first. A task waiting on its check-back is looked at every `EXTERNAL_WAIT_CHECK_MS` (5 min) while dispatch is open, as after a restart (`checkExternalWaits`): with no enabled job left (a one-shot disabled after an interrupt or its retries, a bad interval held disabled, a job removed), it is queued with a "check-back missing" input instead of waiting until the next start. A task whose turn ends with no input pending and no check-back while its own background work runs (`hasBackgroundWork`: a background subagent or command) waits on it (`waiting(external)`, `BACKGROUND_WAIT_REASON`) instead of getting "continue" turns: the report wakes it (`onBackgroundReport`); `checkExternalWaits` wakes it with a "no longer running" input once the work is gone with no report (a restart ends it), and with a "still running" one after `BACKGROUND_WAIT_MAX_MS` (an hour) while work that never ends (a server) runs.
- **Restarts.** Startup is two calls. `recoverAtStartup()` runs in `Agent.start()` BEFORE any channel starts ingesting: it reads the table and runs recovery, reconcile and the sweep; until it returns, `available()` is false, so every entry point (the task tools, relays, cron fires, background reports) refuses. `start()`, after the channels and the inbox replay, opens dispatch: no `schedule()`, `startTask()` or driver runs before it (input that arrives in between is appended and waits; a `startTask()` asked for in between is owed and made first when dispatch opens, past the slot cap), and the notices and report wakes recovery produced are sent then. Recovery is ONE synchronous, idempotent pass (`recover()`); if it throws, sub-sessions stay off until the next start. An active task goes back to `queued` with `resumeNeeded` (more than 3 in a row → failed); so does a waiting one that still owes inputs it does not hold on purpose (`heldThrough`, set by a pause or a self-restart); a first turn cut short gets the start event AND the resume warning. Each decision is one write that also leaves the state that triggered it, so a crash mid-recovery and a second pass give the same table. A task that restarted Tomo itself (`RestartCoordinator` → `restartRequested`, withdrawn if the restart is not launched) waits for the owner. Every destructive cleanup (unlinking a registry entry, archiving or forgetting a task, removing its cron jobs) goes through ONE check, `mayCleanUp()`: the table this process started from was the primary read cleanly (or none yet) and is not marked `untrusted`, and the record is not `restored` (read from `.bak`, so its status may be older than what happened; cleared by a live `task_finish` or cancel, never set on an ended record and dropped on any move to an ended status, since cancelled, failed and archived never change). Neither mark ever ends on its own (no time limit, no count of what is left; a registry that reads as empty proves nothing): a `.bak` recovery tells the owner once, marked `notified` only once the notice went out (a failed send, or a start cut short, tells them again next start) (`tableRecovered`: how many records are restored, how many registry task conversations the table does not know), `/s` lists it first, and only the owner's `/s trust` (`SubsessionService.trust`, refused while the registry is unreadable) drops `untrusted` and every `restored` mark and unlinks the registry task entries the table does not know (ids stay reserved). A table found missing while the registry holds task sessions is marked `untrusted` ("lost") the same way. While the session registry is unreadable, `task_spawn` refuses and no new task id is given out (a spawn first reserves ids past every `task:` key the registry links, so a lost table cannot hand out an id whose conversation still exists), and no turn is dispatched (`mayRun`, asked by every start and every driver turn, unless the key has a live session): a fresh process's last-good state is empty, and the turn would start a new SDK conversation without the task's history; the task is held (no driver re-kicks it until the recheck, `registryHeld`; an owner's start stays owed and is made past the cap when the hold ends), the owner told once, and `REGISTRY_RECHECK_MS` looks again. Readable, with no SDK session for a task that completed a turn, it fails rather than start over. Reconcile acts on nothing the session registry says while it is unreadable (`registryReadable()`: an unreadable registry answers "no task sessions", which is not true). It never unlinks a registry entry unless, in addition, the table read cleanly and holds tasks; it reserves the ids of registry task keys the table does not know, and fails an open task with no SDK session only if a turn of it ever completed (otherwise it starts over). A missing table next to an unreadable `.bak` is unreadable, not empty (sub-sessions stay off). An unreadable cron store is "unknown" (`cronJobCount` → undefined), never zero jobs: no check-back is called lost and a task is parked, not auto-continued. A report is marked delivered only after its wake is scheduled; a note that could not be written is retried in-process. A later `task_finish` never replaces a report still unread (its note waiting, or never written): it is kept in `earlierReports`, uncapped (task_status shows it, the sweep keeps the task while its note waits). A task that fails hands the owner's unanswered inputs back in full as a pinned `subsession-handback` note (`handedBack` once it is on disk; the 30-day forget waits for it and retries), and the failure notice quotes them.

### Tomo's home

A low-poly 3D room Tomo designs as DATA and the web UI draws (`docs/web-ui.md`, "Home"). Format and contract: `src/home/scene.ts`, `status.ts`, the home types in `src/web/protocol.ts`; starter `starter.ts`. Daemon side: `check.ts` (whole-scene check, plain-sentence problems), `floor-plan.ts`, `store.ts` (watch + last good), `files.ts` (the ONE careful reader, also used by the web process), `status-reducer.ts` + `service.ts` (bus → `HomeStatus`, publishing, the picture broker), `weather.ts` (sky; wttr.in + solar position), `snapshot.ts`. Tool: `src/mcp/home-tools.ts` (`home_check`). Skill: `defaults/skills/home/SKILL.md`, whose `{{home:<name>}}` placeholders are filled from the constants by `src/home/skill.ts` when `syncBundledSkills` (`src/workspace/bundled-skills.ts`) copies it — never retype a list there. Invariants:
- **Data only.** Nothing in a scene runs; a new behaviour is a new REACTIONS entry implemented in the renderer, never something a scene defines.
- **Last good.** A broken or unreadable `home/scene.json` never takes the room down: the last good scene (persisted in `~/.tomo/data/home/`) or the starter is served, with the problems.
- **Assets confined.** Every home file is read through `files.ts`: real `home`/`home/assets` directories only, ordinary single-link files, `O_NOFOLLOW`, re-checked after open, size caps, names matched before joining. Nothing under `memory/private` can be served, checked or echoed.
- **Owner only.** `home_check` is registered on the owner's DM session only and refuses a summoned-group turn; subagent `task` text follows the Tasks panel's visibility rule. On a barred turn (the private-memory bar: a group session or a summoned turn) `<workspace>/home/` is the second barred directory, WRITE-only: the PreToolUse hook denies Write/Edit/MultiEdit/NotebookEdit under it (`isHomeWrite`, same `landsInPrivate` rules), and the Bash sandbox profile adds `(deny file-write* (subpath <home>))`, resolved and failing closed like the private dir. Reading the home stays open. An allowlisted group's unsandboxed shell (`groupShellAllowlist`) is full trust here too.
- **Presence.** `home_check` asks a browser for a picture only if `GET /home` was read in the last 90 s (`PRESENCE_MS`; the page re-reads at least every 60 s); otherwise it answers at once. The weather's two-hour "wanted" window is separate.

### LCM (Lifecycle Management)

Custom context management that operates on the SDK's JSONL session files directly (`src/lcm/`):
- `compact.ts` / `stats.ts` / `prune-tools.ts` — range summarization, usage breakdown, tool-result pruning
- `blocks.ts` + `runner.ts` — hierarchical rollups (daily → weekly → monthly → yearly summary blocks); the runner nudges the agent when a completed period is due for promotion
- `chain-check.ts` — every rollup/compact entry point (`tomo lcm <level>`, `tomo lcm compact`, `lcm_rollup`) goes through `compactSessionChecked`: the staged rewrite is written under the same session id into a throwaway sibling project dir and loaded with the SDK's own `getSessionMessages`; only if the new block, the older blocks and the fresh tail are all on that chain is it published (archive, rename, trigger). Otherwise — or when the loader cannot read the session at all — nothing is written and an error is returned (fail closed). SDK appends during the check go through the existing late-arrival splice. `tests/lcm-chain-contract.test.ts` runs this against the installed SDK, so an SDK upgrade that changes how the loader reads a rewritten transcript fails there first

Any code path that rewrites a JSONL file it just read must call `parseJsonl(text, { preserveUnparseable: true })` and write records back with `serializeJsonlRecord` — the default tolerance drops malformed lines, which is fine for a reader and permanent data loss for a rewriter. Opting in widens the element type to `(T | RawJsonlLine)` (see the exported `SdkEntry`), so the compiler forces you to narrow with `isRawJsonlLine` before touching any field. Call `reportRawJsonlLines` after parsing so preserved corruption is visible in the logs. Read-only consumers keep the default.

The harness emits context nudges at `lcm.nudgeAtPct` usage (default 70%, `src/config.ts`), escalating prune → daily rollup → full compact at 80% (decision logic in `src/agent/context-nudge.ts`). A compact reloads the session, so the rollup gate defers it while any background task runs (`src/agent/compact-reservations.ts`); to keep a stream of new subagents from deferring it forever, at `lcm.blockSpawnAtPct` (default 80) the PreToolUse background-launch hook refuses a NEW background Agent/Task launch (`src/agent/spawn-gate.ts`). It reads the nudger's own number (the live session's `lastResult`, an estimated reading counts as unknown) live per call, so it lifts once usage drops; SendMessage, foreground subagents, `task_spawn` and the lcm commands are never gated.

**Forced compaction** (`agent/force-compactor.ts` + `lcm/force-compact.ts`): when a turn ends at or over `lcm.forceCompactAtPct` (default 95; 0/100 off) or on "Prompt is too long" (`isContextOverflowError`, the CLI's local refusal included), the harness compacts the session itself, not its model. Synchronously at the end of that turn `LiveSessionManager.holdForForceCompact` takes the session's one rewrite slot (`CompactReservations.reserveForced`: skips the background checks, never shares the slot with a `tomo lcm`/`lcm_rollup` rewrite) and holds the key like /rewind, so no turn runs until it is done. `quiesceForForceCompact` lets a running turn end (bounded, then interrupts), records the background tasks as interrupted in the running-agents ledger (`markSessionInterrupted`, on disk BEFORE the close; a failed write aborts), closes the session (that stops them) and waits for its CLI child. On disk, everything works on ONE coordinate system, the active chain (`activeChain`: parentUuid walked back from the newest conversation record, cut at the last SDK compact boundary — abandoned branches take no part): selection, summary input, the estimate, the usage ceilings (each record's own ancestors) and the rewrite range, passed by uuid (`CompactRequest.fromUuid/toUuid`; abandoned records inside the run's file span are archived with it). Steps: prune-tools → stop under 70% (estimate calibrated by the last reading, but only one from a turn that reached the API) → summarize the oldest raw stretch (one local day, or a prefix ≤150K tokens never cut before a tool result) with a separate SDK call (`force-summarizer.ts`: no tools/MCP/settings/plugins, not persisted, no titling, 2 retries), published through `compactSessionChecked` as `daily <day>` → on failure the same rewrite with a `[force-archived …]` placeholder → a refused rewrite stops (fail closed). Last, `stale-usage.ts` caps every assistant `usage` above the estimate: the CLI's local window check anchors on the newest real assistant usage on the chain (zero readings are skipped, so capping, not zeroing), and an uncapped pre-compaction reading keeps refusing the compacted session without calling the API. Then a `force-compacted` note and the interrupted-agents note (+ resume turn) are queued inside the hold, and the owner gets one notice (a group: its title only). At most 3 runs per key per hour.

### Localization (i18n)

i18next on both sides, English as the source. Locales: `en`, `zh-Hans` (`src/i18n/locales.ts`).

- **What gets translated** (the catalogs fill in as each surface is converted): fixed text Tomo writes to people. The web UI, chat-command replies, the Telegram command menu, and harness notices to the owner (permission DM, error and MCP notices, cron notices).
- **What is NOT**: anything for the model (system prompt, tomo-event bodies, heartbeat prompts, tool descriptions and results, permission outcomes told to the agent), model output, logs, and the CLI. These stay English.
- **Catalogs**: one namespace per feature, as TS files. `src/i18n/catalogs/<locale>/<ns>.ts` (daemon) and `web/src/i18n/catalogs/<locale>/<ns>.ts` (web). English is `export const <ns> = { ... } as const`; a translation exports the same name `satisfies Translation<typeof en>` (`src/i18n/catalog.ts`). A missing, extra or misspelled key fails `tsc`. Register each namespace in that side's `resources.ts`.
- **Keys** are written out in full at the call site (`t("status.title")`) on a translator bound to its namespace (`ownerT("ns")`, `useTranslation("ns")`, a parameter typed `OwnerT<"ns">` / `TFunction<"ns">`, or an `ns:key` literal). `tests/i18n-catalogs.test.ts` reads those calls from the AST and fails on a key nothing uses, and on placeholders that differ between locales. A key built at runtime must be declared in its file with `// i18n-dynamic: ns:prefix*`; a non-literal key in a file without one fails the test.
- **Plurals and values**: i18next CLDR plurals (`key_one` / `key_other` + `{ count }`; Chinese needs only `_other`; any language may add `_zero` beside an `_other`, even where English has none). A suffix counts as a plural form only when its family has an `_other`, so `step_one` alone is an ordinary key. Interpolate with `{{name}}`, never concatenate translated fragments. Numbers, dates and relative times go through `Intl`, with the active locale passed explicitly.
- **Daemon**: no global language. `ownerT(ns)` (`src/i18n/index.ts`) translates into `config.locale` (unset: English). An owner-facing outlet must take `OwnerText`, which only `ownerT(...)` produces. Model output or a value typed by a person passes through `raw(text)`; never wrap fixed copy in `raw`. `raw` is allowed only in the files listed in `tests/i18n-raw-usage.test.ts`, so adding a use means adding the file there, in review.
- **Web** (the rule for the web UI's i18n setup): locale = the Settings choice (localStorage), else config `locale` (bootstrap), else `navigator.language`, else English. `eslint-plugin-i18next` flags literal JSX text and user-visible attributes.
- **Chinese copy**: short and natural, as a Chinese app would say it, with full-width punctuation. Keep product terms in English where people say them that way (session, agent, MCP, token, cron, Telegram).

## Code Conventions

- ESM throughout (`"type": "module"` in package.json)
- TypeScript strict mode
- Imports use `.js` extensions (Node16 module resolution)
- Logging via `log` from `./logger.ts` (pino) — use `log.info`, `log.warn`, `log.error`, `log.debug`
